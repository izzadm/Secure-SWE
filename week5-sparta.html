1. Why Automate Threat Modeling?

Manual threat modelingAutomated threat modeling
Costs a lot of time and money; earlier results (effort, deliverables) are almost impossible to reuse when the system is later improvedEarlier results can be reused → re-evaluate the improved design
Inconsistent records between analysts make it hard to see the causal relationship between solutions and threatsA catalog that forces all required information to be filled in gives traceability between threats and solutions
—Identify threats and easily evaluate solution effectiveness against a dynamically changing attacker model
Lecture insight — why manual threat modeling is painful Recording: SPARTA, ~05:36–12:12
  • Time and cost are the #1 problem of all threat-modeling automation tools. Drawing the DFD itself can cause analysis paralysis — so much effort on modeling that modeling becomes the bottleneck and delays the whole SDL schedule. Building the attack library, identifying threats, and drawing attack trees are also very time-consuming.
  • It is an iterative loop: threat modeling → risk analysis (decides mitigation order) → apply countermeasures to the system model → re-run threat modeling … until risks no longer shrink.
  • Why previous results were hard to reuse: it was hard to see which solution was applied to which system function. Old approach: write requirement IDs (R1) in the requirements spec, then reference them from design items (D1) and so on — you had to trace through documents. With no documents, someone had to trace through the code by hand.
  • Inconsistent records: like self-introductions — two people describing the same thing (which requirement mitigates which threat) will write it differently. So the causal link between a mitigation and the threat it addresses was hard to establish and reuse for similar products.

Why automation is hard (When / What / How)

  • When: From which point in the SDLC should security/privacy requirements be considered? → At requirements (re-)elicitation, as early as possible.
  • What: Which SDLC artifacts should be considered? An artifact describing system structure and behavior is needed, but no standard or regulation fixes which one (e.g., data flow diagram, state transition diagram) → hard to know what to reference.
  • How: Security/privacy analysis is not one-and-done; it must be repeated across almost all SDLC phases (requirements → design → implementation → verification).
Lecture insight — "artifact" and why threat modeling must be repeated Recording: SPARTA, ~12:12–18:34
  • Artifact = any deliverable produced during development (design documents, code, test results ...). If you prefer, think "development documents." The "requirements" to derive can equally be read as "countermeasures." Structure/behavior artifacts are mostly design documents; since no standard fixes which one, data flow diagrams and state diagrams are referenced.
  • Class Q&A — why repeat threat modeling? A student answered "new problems keep appearing mid-development." The lecturer added three reasons:
    1. New vulnerabilities are discovered during the development schedule.
    2. Mitigation effectiveness changes over time — e.g., a countermeasure meant to reduce risk from 10 to 5 might only reduce it from 10 to 8 after faster CPUs or AI-assisted attacks.
    3. Countermeasures change the attack surface — a security function you add can itself become a new attack target. So repeat until no further threat can be exploited within a realistic time/cost.

Research directions for automation

  • Extended DFD metamodel: build a metamodel so earlier results can be reused and the improved design re-evaluated; metamodel information provides traceability of which threat in the system model can be mitigated by which solution.
  • Threat and solution patterns: automatically analyze how risky a threat is given a dynamically changing system model and attacker; use results to easily evaluate solution effectiveness against threats.

2. Limits of Existing Tools — MS-TMT

MS-TMT (Microsoft Threat Modeling Tool) is STRIDE-based. Key weakness: lacks ways to express security/privacy solutions.

  1. When defining a solution, details can't be expressed.
  2. Solutions that can be expressed abstractly are biased toward encryption.
  • MS-TMT does allow entering some info (e.g., element properties like "Encrypted", "Signed", HTTPS data flow attributes) but it's still insufficient — entering it removes about 20% of threats early, yet:
    • It's hard to tell which security information caused a threat to be removed.
    • Comparing efficiency between solutions is limited.
    • The DFD holds no solution information, so other artifacts must be consulted — which may not match the design (DFD).
    • Applying security/privacy solutions needs knowledge from many fields (results may be inconsistent depending on analyst skill).
  • It also can't express security information or assumptions in a structured way. Consequences:
    • A threat found in past modeling was removed in the current system, but that fact isn't shown in the DFD.
    • A threat was identified earlier but that info isn't in the DFD.
    • Mitigation applied, yet additional threats may still occur.
Lecture insight — why MS-TMT's solution info is so abstract Recording: SPARTA, ~20:32–25:49
  • MS-TMT was designed so that even people who don't know security could threat-model with the tool. Developers can usually only answer coarse questions (is it encrypted? signed? stores credentials? stores logs?) — not details like key length or weak key patterns that you, as security-aware people, would care about.
  • Encryption is visible (encrypted vs not), but access control or auditing can't be judged without a security person — that's why solutions skew toward encryption and everything else stays abstract. Many people don't even fill the solution fields in.
  • The 20% finding (experimentally shown): two groups of volunteers got the same DFD; one group also filled in solution information, the other didn't → about 20% fewer threats were identified in the group that entered solution info.
  • Why that matters (scale): the course example gives roughly 90–100 threats by STRIDE-per-element. A realistic system has about 150–200 DFD elements → roughly 800–1,000 theoretical threats, many of which aren't realizable. Entering solution info correctly cuts the number you must analyze.
  • But MS-TMT still can't tell you which piece of security info removed a threat, nor which of several candidate solutions is more effective, nor show it in the DFD. SPARTA adds solutions to the DFD model and even simulates how much risk each solution takes off.

3. SPARTA — Tool Architecture

Three components, all built on a shared meta-model using the Eclipse Modeling Framework (EMF):

FunctionTechnologyRole
① DFD model (graphical model editor)EMF SiriusDraw the extended DFD (including threat/solution information)
② Threat elicitationEMF VIATRAAutomatically derive threats using query patterns
③ Risk (threat prioritization)Extended FAIR modelScore and prioritize threats

Workflow: Model (from diagram; optionally text/code; plus a knowledge base) → Elicitation (using query patterns) → Threat list → Prioritize / Plot / Export (CSV). Results feed back into the model so the design can be refined and re-evaluated.

Lecture insight — background and the two core ideas Recording: SPARTA, ~03:48–05:36 and ~18:34–20:32
  • Searching "SPARTA" gives two things: this threat-modeling automation tool, and a separate tool/attack library for the space domain. We study the former.
  • Built by the same research team that developed LINDDUN; their technical documents say they used SPARTA to threat-model systems at several European airports/aviation systems.
  • Two key ideas to automatically track "which countermeasure/solution was applied to mitigate which threat":
    1. Extend the DFD metamodel so it can hold threat and security-solution information.
    2. Define threat and solution patterns (rules) so the tool knows which threat can occur at which DFD element and which solution mitigates it.
  • The difference from MS-TMT is exactly this: an extended DFD metamodel + separately defined threat and solution patterns.

4. ① Extended DFD Model

  • A normal DFD model = an abstract set of rules (attributes, relationships, constraints) needed to describe the behavior and structure of the target.
  • SPARTA's extended DFD is developed so the model can also hold threat and solution information.

Key metaclasses

MetaclassMeaning
DFD elementsProcess, DataStore, ExternalEntity, TrustBoundaryContainer, DataFlow (a DataFlowEntity sends/receives DataFlows)
ThreatTypeCatalog / ThreatType (reusable)Catalog of threat types (e.g., Spoofing, Tampering, InformationDisclosure)
SolutionCatalog / Solution / Role (reusable)A Solution (e.g., a secure pipe) defines Roles that elements play (e.g., Server, Client, flows)
CounterMeasureWhat a solution provides; mitigates ThreatTypes and is realized by Roles
SolutionInstance / RoleBinding (model-specific)Applying a solution in a concrete DFD: RoleBindings bind catalog Roles to actual DFD elements
SecurePipe example from the slides
  • DFD: WebBrowser ↔ WebServer with two data flows (df1, df2).
  • The SecurePipe solution has roles Server, Client, Flow1, Flow2.
  • Role bindings map Client → WebBrowser, Server → WebServer, Flow1 → df1, Flow2 → df2.
  • Countermeasures in SecurePipe: AuthN → mitigates Spoofing; MAC → mitigates Tampering; Enc (encryption) → mitigates InformationDisclosure.
  • So from the bound solution, the tool knows which threats in the DFD are covered.
Lecture insight — the "Role" attribute is the trick Recording: SPARTA, ~25:49–33:00 and ~48:28–51:45
  • The normal DFD metamodel: DFD elements are data flows, data-flow entities (process, data store, external entity), and containers (e.g., trust boundary). On its own, it can't show which solution was applied for which threat.
  • SPARTA adds a Role to DFD elements — the first tool to add a role attribute to the data-flow-entity class. "Not a huge thing" — it's basically one extra piece of information, but it makes traceability automatic.
  • Role is about function, not the element's name. The process that requests a service takes the Client role; the process that answers takes the Server role (client–server architecture), regardless of whether it's named "web browser" or "web server."
  • Tracking chain: DFD element → RoleBinding to a Role → Solutions applicable to that Role → each solution's Countermeasure → the ThreatType it mitigates (e.g., an authentication/access-control countermeasure applicable to the Server role mitigates Spoofing). Once you give an element a role, the candidate solutions and the threats they can mitigate are tracked automatically.
  • Old way vs SPARTA: before, you wrote in a document "countermeasure applied to Process 1, so Process 1's threats are removed" and updated the document each time — hard to trace, written differently by each person. SPARTA applies the solution directly to the DFD model.
  • Result in the demo: applying the SecurePipe solution to the model automatically dropped the tampering/information-disclosure risk of one flow (Flow 4) to about 0.02. SPARTA (first made around 2020) was the first to do this kind of tracking; many tools have extended it since, e.g., toward automatic attack tree generation.

5. ② Threat Elicitation (VIATRA)

Problems with plain element-based identification

Pro: simple — derive threats from a mapping table. Con: it ignores which DFD element sends what and in what situation, causing 3 problems:

ProblemExplanationExample
False NegativePossible threats are missed: focusing only on the element misses threats from that element's transaction typesOnly DB-itself threats considered → threats from DB request queries are missed
False PositiveThreats that cannot occur are identified: applying the mapping table without regard to system contextThreats that can't happen in the real environment are listed
DuplicatesDocumented threats overlap: ignoring interaction and data direction yields several threats with the same meaning—

As designs grow complex, accurately finding threats (flaws) from elements and interactions alone has limits.

SPARTA uses 5 kinds of information to elicit threats

InformationRequirement
InformationThe data type must be specified in the model
OperationDescribe how the operations a process performs are carried out
CountermeasureProvide information about the solution
AttackProvide attack methods possible in the system
ActionInclude the actions needed to detect the threat
Example — Security Design Flaw 15: Insecure Data Exposure
  • Description: data not transferred securely, e.g., a web app using HTTP instead of HTTPS → vulnerable to eavesdropping and MITM.
  • Detection steps: locate valuable (sensitive) info in the model → track it through the architecture to see where/how it's transferred → at each step check: replay prevented? timestamp/sequence/checksum used? traffic over an encrypted channel (SSL/TLS)?
  • Turned into pseudocode: for each DFD element and each data type it handles, if the data is sensitive and the element's solution does not protect against tampering or against information disclosure → trigger Design Flaw 15.
Example — Stored XSS as a VIATRA pattern

Detecting flaws like Stored XSS needs complex design information. Stored XSS: a hacker (entity 1) uploads a malicious script (data) through process(es) to the server's data store, and it is later delivered to a normal user (entity 2).

  • VIATRA pattern (xssflaw): ExternalEntity e1, e2; DataStore ds; Process p1; find communication(e1, df, p1); neg find mitigation(p1, df, "Tampering") (i.e., no tampering mitigation); find FlowTo+(p1, ds) and FlowTo+(ds, e2) (the + means a path of one or more flows).
Lecture insight — "duplicate" threats explained Recording: SPARTA, ~33:00–35:50

Example: a tampering threat on a data flow. One analyst records tampering at the data flow; another says the sending process is responsible, so records it there too; a third also blames the receiving process. Now one threat appears in three places — same threat, listed at where it happens, what causes it, and what it affects. In a complex design, such false/duplicate results explode in number. That's why SPARTA moves from "one element → one threat" rules to richer patterns over several DFD elements and their data flow.

Lecture insight — Controlled Natural Language (CNL) → VIATRA pattern Recording: SPARTA, ~35:50–47:17
  • Weakness descriptions (e.g., CWE) are written in natural language, and different people describe the same thing differently. If each person turned them straight into tool patterns, patterns would vary and contain errors.
  • SPARTA's fix: first extract the 5 pieces of information (Information, Operation, Countermeasure, Attack/how, Action) into a template → a Controlled Natural Language (CNL) / template-based description → then model it as a pattern in the VIATRA modeling language. (CNL = natural language written in a fixed way.)
  • Stored XSS example: a hacker (external entity) uploads a malicious script through process(es) into the server's data store; a normal user (another external entity) later gets it through some process. Pattern: external entity → process → data store → process → another external entity. The two entities must differ; the two processes may be the same; the data store must be shared. (Other path shapes also count as stored XSS.)
  • Why VIATRA? SPARTA's DFD model is built on Eclipse Sirius and its threat patterns on Eclipse VIATRA. To add a new threat, define a new pattern in VIATRA in the pattern library — the lecturer says about a week of work in a research lab (set up Eclipse and the VIATRA packages).
  • Net improvement: (1) threats are identified through patterns; (2) which solution mitigates which threat is shown in the DFD modeling space itself.

6. ③ Risk Assessment (Extended FAIR)

Formula tree (memorize)

Core formulas
  • Risk = LEF × LM (Loss Event Frequency × Loss Magnitude)
  • LEF = TEF × V × RP (Threat Event Frequency × Vulnerability × Retention Period)
  • TEF = PoA × CF (Probability of Action × Contact Frequency)
  • V = Max(CD, CB) (Countermeasure Defeated, Countermeasure Bypassed)
  • CD = f(TC, S) where f(x, y) = 1 if x ≥ y, else 0 (TC = Threat Capability, S = Strength)
  • LM = AV + PV (Asset Value + Privacy Value)
  • PV = DTS × NR × DST × NDS
TermMeaning
RiskOverall risk level
LEF — Loss Event FrequencyRate at which a security incident or privacy violation occurs
TEF — Threat Event FrequencyRate at which a threat is attempted (not whether it succeeds)
PoA — Probability of ActionProbability the actor performs the act (depends on reward, capability, opportunity given to them)
CF — Contact FrequencyHow often the threat actor interacts with the system
V — VulnerabilityProbability that a security/privacy threat occurs
CD — Countermeasure DefeatedProbability the countermeasure is defeated; compares attacker capability (TC) against the strength (S) of the security/privacy function
CB — Countermeasure BypassedWhether a way exists to bypass the countermeasure (assessed similarly; the model links it to Insider)
RP — Retention PeriodHow long data is stored or processed
LM — Loss MagnitudeImpact of the security/privacy threat
AV — Asset ValueLoss/damage to the organization if the attack succeeds (can be expressed in money)
PV — Privacy ValueImpact on the data subjects
DTS — Data Type SensitivityConfidentiality level of the data
NR — Number of RecordsRecords processed/stored (same data in many records → high impact; only in a few → lower)
DST — Data Subject TypeType of subject whose data is handled (e.g., children → higher risk)
NDS — Number of Data SubjectsHow many data subjects

Other parameters

  • System Context: DFD elements affected by the threat, applied solutions, asset value, etc.
  • Threat Type: which threat types remain
  • Attacker Profile: extra info on attacker capability
  • Data Subject Type and Data Type

Monte Carlo simulation

  • SPARTA runs risk assessment automatically with Monte Carlo simulation over the metrics above.
  • Monte Carlo: repeatedly generate random values (random numbers) from a probability model, simulate with them, and find the probability distribution of the answer.
  • Each input (S, TC, CF, PoA, ...) is a distribution; they combine up the tree (e.g., V from P(TC > S); TEF = CF × PoA; LEF = V × TEF; R = LEF × LM).
  • Output (slide screenshot): a ThreatAnalysis view listing each threat (e.g., Information Disclosure on the Database) with risk in money, annualized loss, mitigated vs. residual risk, under a chosen attacker model (e.g., "Motivated, capable, organized").
Lecture insight — how much of the risk math you need Recording: SPARTA, ~48:28 and ~51:45–52:42
  • Risk analysis in SPARTA uses Monte Carlo simulation (statistical virtual simulation) to score how risky each threat is — the tool outputs numbers like 0.75, 0.71, 0.77. The lecturer deliberately cut the detailed risk-formula material from the lecture slides as not essential.
  • Exam focus (lecturer's words): know what manual threat modeling looks like and exactly how SPARTA automated it — i.e., how it extended the existing approach. Everything else is detail.
  • Newer automation research is expanding to risk analysis and automatic attack tree generation; the lecturer's lab also published automotive threat-modeling automation work.
