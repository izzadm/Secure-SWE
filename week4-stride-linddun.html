1. What is Threat Modeling?

A methodology that uses a systematic procedure to identify known security threats that could occur in a product.

StageDescription (guiding question)
System modelingAbstract the target system by referring to data flow ("How does the system work?")
Known threat information gatheringCollect known vulnerabilities/attacks related to the system ("What hacks happened to it in the past?")
Threat analysisDerive threats that can occur in each system component ("What threats are inherent?")
Attack scenario derivationTurn the threats into scenarios showing the order in which they could be exploited to compromise the system ("How does a hacker attack?")
Mitigation (countermeasure) planningDerive security measures to counter the attack scenarios ("How do we protect the system?")
Real-world result — Microsoft

Per-stage processes reduce vulnerabilities found after release, and removing vulnerabilities before release reduces cost. Chart on the slide: Windows XP (SDLC) = 119 → Windows Vista (SDL) = 66, a 45% decrease.

2. STRIDE Threat Modeling — Overview & Process

  • Proposed by Microsoft's Praerit Garg and Loren Kohnfelder to improve the security of Microsoft's own software.
Lecture insight — where STRIDE came from Recording: STRIDE & DFD, ~00:00–03:21
  • Same overall flow as the MS-SDL threat modeling from Week 3, but with the detailed steps (known-threat collection, attack scenario derivation) spelled out.
  • Proposed by Microsoft researchers around the late 1990s–early 2000s, built from Microsoft products' real vulnerabilities: causes and effects were grouped into categories (spoofing, tampering, repudiation, information disclosure ...).
  • Original goal: remove threats in Microsoft products early to cut development cost. Because Microsoft products (Windows, SQL Server) are everywhere, papers now call STRIDE a general-purpose method — the first one to try on general software.
  • Limitation: domains where Windows/MS products can't be installed (military, vehicles) use other threat-modeling methods.
  • One-word purpose of the risk-analysis (DREAD) step: prioritization.

Process (in order)

  1. Diagramming — create the DFD
  2. Attack Library — collect known vulnerabilities
  3. Threat enumeration — identify threats per DFD element/interaction
  4. Attack Tree — turn threats into attack scenarios
  5. Remediation — choose countermeasures
  6. Risk analysis (DREAD) — prioritize which to mitigate first
StepPurposeKey points
DFDExpress data flow between processes during analysis/design; used for system modeling4 elements (External Entity, Process, Data Store, Data Flow); splitting processes makes data flow per structure easy to follow
Attack LibraryCollect currently known vulnerabilities for the target to use in threat identificationBased on CVE, CWE, etc.; the more accurate/numerous the collected vulnerabilities, the more useful for identification
Threat enumerationIdentify security threats in DFD componentsSTRIDE-per-element, STRIDE-per-interaction
Attack TreeProtect the system from various attacksShows, as a tree, how an attacker could achieve a specific attack
RemediationDerive mitigation for identified threatsConsider security functions that can block paths so attack scenarios are efficiently mitigated

Step ① — Create the DFD

ElementDefinitionExample
External EntityThings outside your controlPeople, other systems, web sites
ProcessCodeExes, assemblies, COM components
Data FlowHow information flows between other elementsFunction calls
Data StoreData at restFiles, databases, registry keys
  • Also add a dotted-line Trust Boundary: marks the border between locations operating at different privilege levels.
  • Strip everything unrelated to the analysis target — keep only essential information.
Quality criteria for a DFD
  • Completeness: every function of the real target must be included in the abstracted diagram.
  • Soundness: the difference between the real target and the abstracted diagram must be small.
Lecture insight — how to decide which DFD element something is Recording: STRIDE & DFD, ~03:21–07:44
  • External entity = everything outside the scope you are analyzing. Analyzing a PC → the user and any external server the PC talks to are external entities.
  • Process = any program or piece of source code (an app, a running system library).
  • Data flow = input parameters, return values, outputs — anything transmitted between elements (drawn as arrows).
  • Data store = anywhere data is stored: memory, a database's storage, a USB/removable disk.
  • Common confusion — databases: the managing software (the DBMS) is a process; the storage space it manages is the data store. A query goes to the process and a value is returned.
  • Trust boundary = where the privilege required to send/receive data changes (classic example: user → login process). Draw it explicitly as a dotted line.
Lecture insight — why the trust boundary matters Recording: STRIDE & DFD, ~08:32–13:37
  • A DFD keeps only the data flow and deletes everything else. Threats can occur at every element (STRIDE-per-element), but real attacks concentrate where data crosses the trust boundary — the external interface is where cyberattacks start (SQL injection into a login process, brute-forcing ID/password, social engineering to impersonate a user).
  • So always draw those data flows and analyze their threats in more detail.
  • Link to the MS-SDL "security assumptions" step: you may assume the area inside the trust boundary is safe (e.g., strictly runtime-monitored) and skip threats found there by STRIDE-per-element; or you may assume it is not safe, because threats inside can later be chained with external attacks. The boundary-crossing parts are analyzed either way.
Lecture insight — Completeness vs Soundness, with examples Recording: STRIDE & DFD, ~13:37–19:17
  • Modeling = keep only the information you need and delete the rest (simplify a complex target). The danger: a gap between the real target and the model.
  • Completeness broken: the real system has 6 functions but the model has only 4 processes (unless those 4 truly cover all 6). Likewise 5 real functions (A, B, C, D, E) but only 4 appear in the model.
  • Soundness broken: all functions are present, but the meaning differs — e.g., really A calls B (or C or D), then E, then E calls A recursively, but the model draws A→B→E→A. Same functions, different call semantics.
  • Soundness = the semantic difference between the real target and the abstracted model must be small. There's no single "correct" DFD; the goal is to draw it as accurately as possible.

3. Step ② — Build the Attack Library

Collect security threats/vulnerabilities that can occur in the target or similar products. Why: if you map threats using only STRIDE's identification rules, results can be too abstract or unrealistic. Sources: papers, standards, technical reports, vulnerability databases.

CWE (Common Weakness Enumeration)Security-flaw database that classifies weaknesses (not just vulnerabilities), based on vulnerabilities in the CVE database
CAPEC (Common Attack Pattern Enumeration & Classification)Database of attack patterns that arise when a weakness is exploited; a pattern may include definition, prerequisites, likelihood, consequences, mitigations

Lecture insight — what each database really is Recording: Attack Library, ~00:00–11:44
  • Attack library info can come from papers, standards (annex-style lists of threats/vulnerabilities), vendor technical reports on product vulnerability analysis — but the most used source is the vulnerability databases.
  • CVE = vulnerabilities found in actual products (like a bug-bounty report: described, often with PoC code and procedure). Each entry also carries CPE (Common Platform Enumeration, "product enumeration") — which product or product family is affected. For an attack library, CPE is the key field: use it to decide whether a collected vulnerability is related to your target.
  • CWE = groups vulnerabilities into common but somewhat abstract types (weaknesses).
  • CAPEC = attack techniques/procedures used to exploit a weakness (example: how to reach the kernel and set register values to escalate privilege without authorization).
  • MITRE ATT&CK = built from real attack cases. Tactics are the attacker's goals (the columns: reconnaissance, resource development, initial access, execution, persistence, privilege escalation ...); Techniques are the detailed methods to reach each goal (e.g., "Scanning" under reconnaissance to collect IPs and open ports).
  • In short: CVE = a specific product's flaw; CWE = flaw type; CAPEC = how the flaw is exploited; ATT&CK = what an attacker is trying to achieve and how.
Lecture insight — ATT&CK also helps write attack scenarios Recording: Attack Library, ~07:32–10:55

Tactics are ordered: achieving earlier goals (initial access, then execution ...) leads to the final goal (e.g., exfiltrating data). Because of this causal ordering, ATT&CK is also used after threat identification to write attack scenarios. Active research links ATT&CK (abstract goals/techniques) → CAPEC/CWE (weaknesses) → CVE (concrete flaws) to produce scenarios at CVE level. For this course, just remember ATT&CK is one vulnerability database you can use for STRIDE-per-element.

Lecture insight — why build an attack library at all? Recording: Attack Library, ~12:41 and ~27:17–29:46
  • STRIDE-per-element threats are abstract. If threats aren't concrete, the attack tree is abstract too, and you may end up planning mitigations for threats that can't happen in your product or that can't be properly applied. Concrete identification → accurate scenarios → accurate countermeasures.
  • "Why not just search the CVE site when needed?" The key is collecting vulnerabilities related to your product — unrelated ones are meaningless.
  • It's not a one-time step. Building the library is time-consuming and vulnerabilities are constantly added/updated, so you keep updating it throughout the whole threat-modeling process (that's why it isn't "done" once at step 2).
  • CVE website practice: search by product/category (e.g., "infotainment") to get related vulnerabilities, descriptions, references (with more detail and PoC).

Lecture insight — per-element vs per-interaction, in practice Recording: Attack Library, ~13:43–20:39
  • Per-element: one element type → fixed list of threats. Counts per element: external entity 2, process 6, data store 3 (4 with the △), data flow 3. Multiply by how many of each element are in your DFD to get the theoretical threat count. Simple and fast, but the results are abstract.
  • Per-interaction: look at data exchanged between two elements and brainstorm the threats there — more concrete, but it depends on the analyst's knowledge, takes longer, and is more complex.
  • Bluetooth example: per-element gives "attacker pretends to be a legitimate user while Process A communicates." Per-interaction (with Bluetooth knowledge) finds Bluetooth-specific issues, e.g., spoofing the beacon signals that a device sends to find devices to connect to. Per-element can't see "Bluetooth" at all — it only looks at the table. The attack library fixes this: map the abstract threat onto real vulnerabilities for that technology.
  • MS-TMT (the tool you'll practice with) identifies threats with STRIDE-per-interaction: the analysts' product-vulnerability knowledge was turned into patterns the tool applies automatically, so it feels as easy as per-element even though it is per-interaction underneath.

5. Worked Example — ID/Password Authentication System

Target: a remote ID/Password-based authentication system for customers accessing a system. DFD elements named in the slides: E1 Clients, P1 Log-in, D1 Account Database, DF7 Client ID/Password & personal information.

Procedure

  1. Build the Attack Library (previous section).
  2. List abstract threats per DFD element using the STRIDE-per-element table. Example: for external entity Client → Spoofing ("attacker pretends to be a legitimate customer") and Repudiation ("attacker denies having accessed the system").
  3. Make the abstract threats concrete with Attack Library entries. Example: Spoofing of the client becomes — replay attack to impersonate (AL-V-3, AL-W-3, AL-P-2); phishing-collected ID/PW (AL-V-5); vendor default account to pose as admin (AL-V-4).
  4. Threats with no supporting library entry — the slides show these being removed (e.g., Repudiation above is dropped in the example). But see the lecturer's nuance in the box below: absence of a known vulnerability does not prove the threat is impossible.
  5. Final threat table with columns: location (DFD element), threat type, description, attack library refs, threat number (T1, T2 ...). The slides list T1–T18.
Sample rows from the slides
  • T5 (P1 Log-in, Tampering): XSS vulnerability lets attacker log in as admin → AL-V-2
  • T6 (P1, Info disclosure): weak password rules + info in error messages → guess ID/PW → AL-V-1, AL-W-2, AL-P-1
  • T7/T8 (P1, Info disclosure): monitor unencrypted traffic / break weak encryption → AL-W-5, AL-W-6
  • T9 (P1, DoS): mass packet attack → AL-V-6
  • T10 (P1, DoS): no/faulty exception handling, tampered data puts system out of control → AL-V-7, AL-P-3
  • T11 (P1, Elevation of privilege): abuse vulnerable functions like strcpy, strcmp to get root → AL-W-1
  • T12/T13 (D1 Account DB, Info disclosure): unencrypted storage / weak encryption → AL-W-5, AL-W-6
  • T14 (D1, DoS): Ping of Death, SYN flooding → AL-V-6
  • T16 (DF7, Info disclosure): man-in-the-middle captures account and personal info → AL-W-3
Lecture insight — turning an abstract threat into a concrete one ("add the how") Recording: Attack Library, ~20:39–25:30

The abstract threat "attacker spoofs a legitimate client" has no how. The attack library adds it: replay attack (AL-W-3: capture the user's packet and resend it), phishing (AL-V-5), default account (AL-V-4). Concretizing answers how the spoof/entry happens and what result it causes.

Lecture insight — filtering library entries by what your product actually is Recording: Attack Library, ~24:55–27:17

The three "replay"-like entries are not the same: AL-V-3 = fake GUI that captures input; AL-W-3 = capture and resend an ID/password packet; AL-P-2 = record a voice and resend it. If your target logs in with a typed ID/password, voice login, or a CAPTCHA/GUI, you can filter which entries apply. In the slide example nothing was filtered because the target was described only abstractly ("ID/password authentication") — if the description said "login by voice," you'd keep AL-P-2 and drop AL-V-3 and AL-W-3. What you can use from the library depends on what exactly you are modeling.

Class Q&A — no library match: exclude the threat? Recording: Attack Library, ~28:52–32:10

Question to the class: if a STRIDE-per-element threat has no matching vulnerability in your attack library, do you just exclude it?

Answer: You can't conclude it is impossible. A zero-day may exist, or the vulnerability may exist and simply be unknown — cases where no one can know. Even a well-maintained library showing no mapping only means it's not exploitable with currently known resources/methods (e.g., future AI with huge compute could change that). So treat it as a potential security threat: keep it in mind and carry it into attack scenario / attack tree work as needed, rather than discarding it.

Note: this is a nuance compared with the slide example, which simply removes such threats. If a question asks, the safe answer is "treated as a potential threat; not proof it can't occur."

Lecture insight — the threat count can go up after concretizing Recording: Attack Library, ~33:15–37:29
  • Example DF7 (client ID/password & personal info) has two different information-disclosure threats: (1) guessing from weak password rules / error messages, (2) man-in-the-middle capture. Different exploitation methods = separate threats, even though the STRIDE category is the same.
  • Theoretical per-element total in the example: 18 + 27 + … = 47 threats. After applying the attack library, the count can rise (e.g., 50, 60 ...) because one threat may split into several concrete ones. That is normal, not an error. Concretizing can also decrease the number.
  • Writing the attack scenarios from these threats is largely qualitative/manual; research is trying to automate it (e.g., via ATT&CK ordering).

6. Step ④ — Attack Tree

A tree-shaped diagram of attacks on a system; lets you derive attack scenarios from the identified threats.

  • The single root node (top) = the attacker's final goal.
  • Leaf nodes = the sub-methods (i.e., threats) needed to reach the goal.
  • Build by decomposing the goal repeatedly.
  • Use AND and OR nodes as the conditions to reach the parent goal.
Slide example (weapon system)

Root: Combat cannot be performed ← (OR) Weapon-control function paralyzed / Command function paralyzed ← each via related data tampering ← man-in-the-middle ← leaves: impersonating the linked system and unencrypted data.

Lecture insight — how to draw it: top-down, bottom-up, AND/OR notation Recording: Attack Library, ~37:29–44:22
  • You can build the tree top-down (start from the goal and decompose) or bottom-up (start from known threats and ask what they lead to). Either is fine.
  • Parent node = the goal; child nodes = the conditions or methods to achieve it. Root = attacker's final goal; leaf = detailed method.
  • Worked example (ID/password system): goal "steal personal info" needs the ID and the password at the same time → AND. To get the ID, you may sniff/capture packets and crack them or use social engineering (either one is enough) → OR. Same for the password.
  • Notation: AND = an arc across the edges, or a straight line joining the edges. OR = no mark at all (any one child satisfies the parent).
  • Sequential AND (seen in some papers): an AND with an arrow showing order — condition 1 must be satisfied first, then condition 2. For this course, only AND and OR are needed.
  • Other attack paths for the ID/password example include phishing and brute force (exhaustive/dictionary attack — the same idea as in cryptography courses).
Lecture insight — no single right answer; how the lecturer does it in research Recording: Attack Library, ~45:03–50:39
  • No fixed method for writing attack scenarios. The lecturer's research approach: traverse the DFD as a graph from an entry node to the node holding the asset (e.g., the DB with IDs/passwords), focusing on data flows that cross the trust boundary; apply STRIDE-per-element to the elements along each path to auto-list threats; then concretize with the library and add ordering/pattern analysis to derive scenarios automatically.
  • An attack tree is itself a model (like the DFD) — so the same rule applies: there's no "correct" tree, aim to be as accurate as possible (completeness and soundness).
  • Number of attack trees = number of distinct final attacker goals: could be 1, 2, 10, or 2,000.
  • Real-world takeaway: to write good scenarios, concretize threats well and collect as many relevant attack-library entries as you can.

7. Step ⑤ — Remediation (Countermeasure)

Choose security functions that block the path so each attack scenario is mitigated efficiently.

AND vs OR — very likely exam question
  • AND node: blocking just one child node neutralizes that whole path.
  • OR node: you must block all child nodes to neutralize the path.

Which child to block? Compare the cost of implementing the security function for each child node, and whether your organization can reuse functions it already has.

Slide example — security requirements
  • Transmitted data confidentiality: the weapon system must protect sent/received user data from unauthorized leakage.
  • Secure channel: logically separated from other channels, guarantees end-to-end identity, and prevents tampering and leakage.

8. Step ⑥ — Risk Analysis: DREAD

Microsoft's five criteria for quantitatively rating the risk of attack scenarios → used to set mitigation priority. Each threat is scored on five aspects (the slide says 1–10 per aspect, with anchors at 0, 5, 9/10).

FactorQuestion0510
Damage potentialHow far does damage spread?No spreadPersonal user data affectedSystem/data fully destroyed
ReproducibilityHow often/easily can it be attempted?Very hard/impossible; admin-level rights needed1–2 steps; specific user-level privilegeOnly a web browser; no privilege
ExploitabilityHow much effort is needed?Advanced programming/network knowledgeUnderstand/use publicly available infoBasic browser features suffice
Affected usersHow many users hit by the same attack?Single user or noneSome (not all) usersAll users
DiscoverabilityHow likely is the flaw to be found?Very hard; needs source code / admin-only screenGuessing or network sniffing9 = listed on a public index such as Shodan; 10 = easily found with only a browser
  • Apply mitigations in order of the sum or average of the five scores, highest first.
  • DREAD is not the only scheme — organizations may define their own scoring criteria to fit their systems.

9. LINDDUN Threat Modeling (Privacy)

Proposed by researchers at KU Leuven; the goal is to identify privacy-related threats (STRIDE is security-focused).

Background: privacy

  • Definition: the right to control, edit, manage, and delete information about yourself, and to decide when, how, and to what extent it is passed on to others.
TypeGoal / assumptionProperties
Hard privacyAssumes third parties are not trusted → minimize privacy information (data minimization)Unlinkability, Anonymity, Pseudonymity, Plausible deniability, Undetectability, Unobservability (+ Confidentiality)
Soft privacyAssumes the data holder is honest → process data per purpose and consentContent awareness, Policy & consent compliance

Privacy properties

PropertyMeaning
UnlinkabilityAttacker cannot tell that two or more items of interest (subjects, messages, actions…) are linked
AnonymityAttacker cannot sufficiently identify a specific person among multiple subjects from the info available
PseudonymityHides identity by using an identifier other than the subject's real name
UndetectabilityAttacker cannot sufficiently tell whether an item of interest (IOI) exists; protects the IOI directly (anonymity/unlinkability protect it indirectly by hiding relationships)
UnobservabilityUndetectability + anonymity combined: cannot tell what the IOI is or who is related to it
Plausible deniabilityCan deny having done something that others cannot confirm or refute; attacker cannot prove a user knew/did/said something
Content awarenessUser is aware of how their personal info is being used
Policy & consent complianceThe system complies with (data protection) law, policy, and user consent

Watch out

In STRIDE, Repudiation is a threat (attacker denies actions). In LINDDUN, Non-repudiation is the threat — being unable to deny an action harms privacy. Don't mix these up.

LINDDUN process

  1. Create the DFD — same as STRIDE.
  2. Threat enumeration — two sub-steps (below).
  3. Misuse case — write abuse scenarios.
  4. Risk assessment — decide what to mitigate first (DREAD, SEI's OCTAVE).
  5. Remediation — choose countermeasures.

Step ② Threat enumeration

  1. Identify privacy threats per DFD element, like STRIDE-per-element, then filter threats using assumptions and the system's operating environment.
  2. Make threats concrete with the threat trees — a collection of privacy-threat info built by the LINDDUN authors containing: causes of privacy violation, examples, criteria, impact, and additional info.

Slide example — "SNS 2.0 app" (social network)
  • DFD elements: external entity User; processes Portal, Service; data flows User-Portal, Portal-Service, Service-DB; data store Social network DB.
  • Filtering: Portal-Service and Service-DB are data flows inside the trust boundary and need no special high privileges → judged safe, so most of their threats are dropped.
  • Threat tree refinement (Linkability of entity): Before — login/access history links SNS activity to a user's personal info. After — time and location shown in SNS activity can be linked to the user's nationality, residence, etc.

Step ③ Misuse case

Turn each refined threat into a scenario showing how privacy could be violated. A misuse case must include 7 items:

  1. Summary — brief description of the threat
  2. Assets, stakeholders and threats — what/who is threatened
  3. Primary misactor — attacker type
  4. Basic flow — basic scenario for the attack to succeed
  5. Alternative flows — other ways the attack can succeed
  6. Trigger — how and when the attack happens
  7. Preconditions — conditions that must hold for the attack to succeed

Step ④ Risk assessment & ⑤ Remediation

  • Risk assessment decides what to mitigate first; methods: DREAD, SEI's OCTAVE.
2011 version — Privacy-Enhancing Techniques (3 types)2023 version (4 types)
Warn the userRisk mitigation — lower the threat's risk level through various measures
Remove the feature that causes the threatRisk transfer — shift responsibility to another organization (e.g., an insurer)
Mitigate the threat with technical measuresRisk acceptance — risk is low enough to accept
—Risk elimination — remove the system feature that could cause the threat, eliminating the risk itself
