Week 2 — SDLC Models

Basics

  • SDLC = scientific, systematic approach to develop, operate, maintain software. Secure SDLC adds: risk assessment → threat modeling & design review → static analysis → security testing & code review → security assessment & secure configuration.
  • Software crisis: HW cost down, SW cost up. Symptoms: delays, cost overrun, malfunction, hard maintenance. Causes: engineer shortage, management unaware, no methods/tools, complexity.
  • Ariane 5 (1996): 64-bit → 16-bit conversion overflow, no exception handling.
  • Humphrey: software quality is governed by process quality (CMM(i)).
  • 3 core activities: requirements spec · design & implementation · verification & validation.

Timeline

1950s Build&Fix · 1970 Waterfall · 1982 Prototype · 1986 V · 1989 Spiral · 1995 Scrum · 1998 Unified · 1999 XP · 2004 Kanban (software)

Cycle length

Waterfall/defense ≈ yearly · automotive V-model ≈ many months–1 yr · MS SDL 6–12 mo · Agile sprint 1–4 wk (whole cycle ≈ 1–2 mo)

V-model pairing

Requirements ↔ System test · Architecture ↔ Integration test · Module design ↔ Unit test · then Acceptance test.

System test = dev lab environment; Acceptance test = real environment, checks satisfaction.

Agile / Scrum

  • Manifesto: people & interaction > process & tools · working software > documents · customer collaboration > contract · responding to change > plan.
  • Roles: Scrum Master (remove blockers, run events) · Product Owner (own/prioritize Product Backlog) · Dev Team.
  • Backlogs: Product Backlog = customer wish list; Sprint Backlog = items chosen for this sprint.
  • Epic (spans sprints) → User Story (smallest user requirement) → Task; Story point = relative effort.
  • Sprint 1–4 wks · Sprint Planning = kickoff (who/what/how) · Daily Scrum ≈15 min standing: yesterday / today / blockers · Review ≤4 h = validation w/ customer · Retrospective = amplify strengths, log issues, compare est. vs actual velocity.
  • Burndown: remaining work vs days; dotted = plan, solid = actual.
  • Kanban: from Toyota parts bins; visual board of task status; 5 principles.

XP's 12 rules

User Stories · Small Releases · Metaphor · Collective Ownership · Coding Standard · Simple Design · Refactoring · Testing (TDD) · Pair Programming · Continuous Integration · 40-hour week (slide: ≤45h) · On-site Customer. XP ≈ disciplined Build & Fix.

Fault / Error / Failure

Fault = wrong code · Error = wrong internal state caused by it · Failure = wrong observable output. A fault may exist without error/failure for some inputs (y=2x vs y=x²: x=2 hides it, x=1 exposes it).

Week 3 — MS-SDL

Overview

  • 13-stage process for security & privacy; revised twice a year (Jan/Jul); ~12-month cycle; credited with 50%+ fewer vulnerabilities. Not suited to 4–5 month cycles.
  • Recommendation = optional; Requirement = must, with a way to verify.
  • Stages 1–5 covered: Training · Project Inception · Design best practices · Product Risk Assessment · Risk Analysis. (6–13: security docs, secure coding, secure testing, security push, FSR, response plan, release, execute response.)

Stage 1–2

  • Training: everyone attends security training at least yearly; attendance logged; managers must attend.
  • Must follow SDL: enterprise-common products · regularly handles PII · regularly sends/receives internet data · auto-downloads updates.
  • 4 tasks: appoint Security Advisor · build security leadership team · bug tracker with security/privacy fields · set the Bug Bar (fix Critical, Important, Moderate before release).

Attack surface = entry points an attacker can use. ASR 3 steps: ① needed by ≥80% of users? else default off (IIS 6 off vs IIS 5 on) ② who/where can access? (Sasser) ③ reduce privileges (non-admin, not Local System).

Stage 4 — Risk assessment

Decide which parts need threat modeling, design review, pen test, and fuzz scope. Security risk assessment questions (OS, default install, ActiveX, auth, first version?) + privacy impact assessment.

Stage 5 — Threat modeling flow

① usage scenarios ② external dependencies ③ security assumptions ④ external security notes ⑤ DFD ⑥ threat types ⑦ identify threats ⑧ risk ⑨ mitigation.

DFD: External Entity · Process · Data Flow · Data Store · Trust Boundary. Layers: 0 context (all) · 1 (most) · 2 (highly sensitive) · 3 (critical/kernel).

DREAD & mitigation

  • DREAD: Damage · Reproducibility · Exploitability · Affected users · Discoverability; score each, average. Dropped by MS in 2008 (subjective, inconsistent) → Bug Bar from MSRC.
  • Mitigation 2023: Mitigation · Transfer · Acceptance · Elimination. (2011: warn user · remove feature · technical mitigation.)
  • Maturity: 0/1 none or outdated · 2 OK (minimum) · 3 Good (pen-tested) · 4 Excellent (all STRIDE + docs).

Week 4 — STRIDE & LINDDUN

STRIDE process

① DFD → ② Attack Library → ③ Threat enumeration → ④ Attack tree → ⑤ Remediation → ⑥ Risk (DREAD, = prioritization).

  • DFD quality: Completeness (all real functions in the model) · Soundness (meaning close to the real system). No single "correct" DFD.
  • Trust boundary: where required privilege changes; attacks concentrate on flows crossing it. May assume inside is safe (documented assumption) or not.
  • DBMS = process; its storage = data store. External entity = everything outside analysis scope.

Attack Library sources

  • CVE = flaws in specific products (+ CPE = which products affected)
  • CWE = weakness types
  • CAPEC = attack patterns exploiting weaknesses
  • ATT&CK = tactics (goals) + techniques (methods) from real attacks; ordered, so also useful for scenarios

Purpose: make abstract threats concrete (add the "how"). Keep it updated through the whole process. Filter entries by what your product really uses. No match ≠ impossible → "potential threat". Count may rise after concretizing. Given in the exam.

Per-element: fast, simple, abstract, misses interaction threats. Per-interaction: concrete (brainstorm per element pair), slower, depends on knowledge; MS-TMT uses it via patterns.

Attack tree

  • Root = final goal; leaves = detailed methods; parent = goal, children = conditions/methods. Top-down or bottom-up.
  • AND = arc/line across edges (all needed); OR = no mark (any one).
  • Blocking: AND → block one child; OR → block all children. Compare cost, reuse existing functions.
  • Sequential AND = ordered AND (not needed). One tree per attacker goal.

DREAD anchors

Damage: 0 none · 5 user data · 10 system destroyed. Reproducibility: 10 = browser only. Exploitability: 10 = browser basics. Affected users: 10 = all. Discoverability: 10 = easy in a browser, 9 = on Shodan.

Week 5 — SPARTA

Manual vs automated

  • Manual: costly; earlier results nearly impossible to reuse; inconsistent records make solution↔threat causality hard to trace; DFD over-drawing = analysis paralysis.
  • Automated: reuse results → re-evaluate improved designs; catalog of required info → traceability; evaluate solutions against changing attacker models.
  • Why hard: When (as early as possible) · What (no standard artifact: DFD, state diagram) · How (repeat across all SDLC phases).
  • Why repeat: new vulnerabilities · mitigation strength changes (10→5 may become 10→8) · countermeasures change the attack surface (they can be attacked too).

MS-TMT limits

  • STRIDE-based; can't express solution details; solutions biased to encryption (designed for non-security developers).
  • Entering solution info removes ~20% of threats early, but you can't tell why, can't compare solutions, and the DFD holds no solution info.
  • Can't express security assumptions in a structured way.

SPARTA stack

Sirius (DFD editor) · VIATRA (threat elicitation patterns) · Extended FAIR (risk) on an EMF metamodel. Built by the LINDDUN team (used on European aviation systems).

Two core ideas: ① extended DFD metamodel with threat & solution info ② threat and solution patterns.

Extended DFD & Role chain

DFD element → RoleBinding → Role (Client = requester, Server = responder; by function, not name) → Solution (e.g., SecurePipe) → CounterMeasure (AuthN, MAC, Enc) → ThreatType (Spoofing, Tampering, Info disclosure).

Solutions are applied directly in the DFD, so "which solution mitigates which threat" is tracked automatically.

Threat elicitation

  • Element-only problems: false negative (missed, e.g., DB query threats) · false positive (can't occur) · duplicates (same threat at flow + sender + receiver).
  • 5 inputs: Information · Operation · Countermeasure · Attack · Action.
  • Natural-language weakness → template (CNL) → VIATRA pattern. Stored XSS: entity → process → shared data store → process → other entity, no tampering mitigation.

Risk formulas (Extended FAIR) + Monte Carlo

Risk = LEF × LM · LEF = TEF × V × RP · TEF = PoA × CF · V = Max(CD, CB) · CD = 1 if TC ≥ S else 0 · LM = AV + PV · PV = DTS × NR × DST × NDS

LEF loss event freq · LM loss magnitude · TEF threat event freq (attempts) · V vulnerability · RP retention period · PoA probability of action · CF contact freq · CD countermeasure defeated · CB bypassed · TC threat capability · S strength · AV asset value · PV privacy value · DTS data type sensitivity · NR records · DST data subject type (children = higher) · NDS number of subjects.

Monte Carlo: sample random values from probability models repeatedly → distribution of risk; shows how much a solution cuts risk.

Exam focus: problems of manual threat modeling + how SPARTA extended it (Role, patterns). Risk-formula detail is secondary.
