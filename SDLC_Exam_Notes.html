1. Overview

Secure Software Engineering = a methodology for building trustworthy systems.

Software Engineering (SDLC) = a scientific, systematic approach to developing, operating, and maintaining software.

  • Normal SDLC: Requirements → Design → Development → Testing → Deployment
  • Secure SDLC: Risk Assessment → Threat Modeling & Design Review → Static Analysis → Security Testing & Code Review → Security Assessment & Secure Configuration

Why SDLC emerged

  • Hardware development cost decreased over time, while software development cost increased — the "software crisis."
  • Symptoms: schedule delays, cost overruns, malfunctioning software, poor quality → difficult maintenance.
  • Causes of high cost: shortage of engineers, lack of management awareness, lack of methodologies/tools, software complexity.
Lecture insight ~00:00–01:00

The extra cost from schedule overruns actually comes from redoing duplicated work. The "lack of management awareness" point is best understood with an analogy: imagine asking your mom for money to buy an in-game item — she can't relate to why it's necessary. Company executives felt the same way about software: if the business was already making money the traditional way, why bother replacing it with software?

Famous Failure: Ariane 5 (1996)

  • A data type conversion from 64-bit to 16-bit while computing the rocket's horizontal velocity caused an overflow.
  • No exception handling existed for the unexpected value → system entered an error state → rocket exploded.
Lecture insight ~01:48–03:32

Rocket engine control used to be a purely mechanical/aerospace engineering problem — igniting the engine, measuring temperature/pressure, calculating thrust. As these functions were gradually replaced by software, the code that handled conversions and edge cases introduced new bugs. In Ariane 5's case, a velocity value that was a valid positive number in 64-bit form became a negative number once compressed into 16 bits, causing an overflow/underflow and a fatal misreading — leading to the explosion.

Software's growing share & defense-grade requirements

  • Software content in fighter jets: F-4 (1960) 8% → F-16 (1982) 45% → F-22 (2000) ~80–100%.
  • 5,000+ vulnerabilities found; only ~4% of 8,000–10,000 yearly cyberattacks get reported.
Lecture insight ~05:27–07:19

Even everyday OSes like Linux or Windows get hardened/modified before being used in defense systems, because military operations require a higher security grade. For example, defense-grade Windows locks configuration settings that a normal user could freely change (to prevent privilege abuse and exposure to vulnerabilities), and certain filesystem features may be reduced or removed entirely compared to the commercial version.

Process spreads from military → civilian industry

Lecture insight ~08:07–12:21
  • Good-process requirements that started in the military/defense sector are gradually trickling down into civilian industries (e.g., Samsung, Hyundai) because foreign regulators now demand it.
  • Automotive example: UNECE (a EU-linked regulatory body) issued UN Regulation No. 155 — starting around 2024, new vehicles that are not developed following secure software engineering practices can be banned from export to the EU. The core requirement: security requirements must be derived through a rigorous process before development.
  • US regulatory trend: a rule is first created for the military (strictest, since national security can't be compromised) → it's relaxed and adopted into federal law → it's further relaxed into general industry regulation for ordinary companies. This pattern is now repeating in domains like the space/satellite industry.
  • Real-world consequence: countries operating jointly with the US military have been told that if they don't have an equivalent level of cybersecurity capability, the US won't share operational information with them — this reportedly affected next-generation fighter jet (e.g., F-21-related) programs.

3. Build & Fix Model

Definition: No requirements analysis or design phase — jump straight into coding, then keep modifying until satisfied.

Flow: Coding → Product → Problem? → (Yes → Fix → repeat) / (No → Use)

Disadvantages

  • No fixed process or documented deliverables per stage → hard to manage/maintain
  • Team members can't effectively divide work
  • Hard to track project progress
Class discussion ~15:50–17:52

Question posed to the class: "If testing keeps finding no more issues, can we call this product safe?"

Answer given: No — a developer might simply fail to find certain vulnerabilities themselves, and as hacking techniques evolve, the attack surface only grows. Even hiring a "red team" doesn't guarantee full coverage, since real red teams tend to specialize (e.g., web hacking, system hacking, reverse engineering) rather than covering every domain equally. So security testing results are inconsistent depending on the tester's skill/specialty — passing all available tests never proves a product is unconditionally safe.

Lecture insight ~18:51–21:32

The US military used Build & Fix in the 1940s–50s and found that weapons developed this way kept getting breached. This pushed them toward mathematically proving code correctness before deployment, rather than just "code, fix, code, fix." A modern example is seL4 — a kernel whose scheduling and memory-management policies have been converted into mathematical formulas and formally verified; it's reportedly used in helicopters and armored vehicles. This is part of why the US has pushed allied militaries (including Korea) to reach an equivalent standard of secure development.

4. Waterfall Model

Definition: Development proceeds sequentially — like water flowing downward — from planning through installation, operation, and maintenance.

Sequence: System Requirements → Software Requirements → Analysis → Program (Architecture) Design → Coding → Testing → Operations

Advantages

  • Simple, easy-to-understand procedure
  • Easy process management & systematic documentation
  • Good fit for projects with low requirement volatility

Disadvantages

  • Each stage must fully finish before the next starts
  • Deliverables must be near-perfect or errors propagate downstream
  • Users see no visible progress until late
  • A problem found mid-project forces revision of all earlier stages — cost of fixing grows exponentially the later it's found
Lecture insight ~23:28–24:29

If a bug is found during testing, you don't just fix the code — you must also revise the related design and, further up, the related requirements. And it's not just fixing one requirement in isolation: you have to re-check whether that requirement conflicts with other requirements (recall the "trustworthiness" concept from Week 1). Then design, coding, and testing must all be redone. That re-verification loop is what makes late-discovered bugs so expensive in Waterfall.

5. Prototype Model

Definition: An incremental approach — build a prototype, evaluate it, then refine requirements into a fuller specification.

Cycle: Requirements gathering & analysis → Quick design → Design/Prototype refinement ↔ Prototype construction → Customer evaluation → Customer satisfaction → Full-scale development

Advantages

  • Iterative requirement definition captures user needs more fully
  • Easier to spot user requirements & technical issues early
  • Confirmable via a working prototype, not just static docs

Disadvantages

  • Risk of treating the prototype as the finished product
  • Hard to estimate cost/effort with repeated user requests
  • Unclear scope → unclear completion criteria
  • Hard to control/manage the process
Lecture insight ~24:29–25:20

Waterfall and the V-model (below) are considered too slow because they require requirements to be fully finalized before moving on. The Prototype model instead sketches a "big picture" first — e.g., pseudocode instead of full implementation, or a simple class diagram instead of a complete design — and only fills in the details afterward.

6. V-Model

Definition: Extends Waterfall by expanding testing activities. Where Waterfall (and even Secure SDLC) checks Validation of deliverables stage by stage as they're produced, the V-model's mirrored structure emphasizes Verification — matching every implementation artifact back against its corresponding requirement/design artifact, but only after implementation is complete.

Verification vs. Validation

CriteriaVerificationValidation
DefinitionChecks whether an intermediate work product meets the defined requirements for that phaseChecks whether the final software meets business requirements
Perspective"Are we building the product right?""Are we building the right product?"
Evaluated itemsPlans, Requirement Specs, Design Specs, Code, Test CasesThe actual software product
ActivitiesReviews, Walkthroughs, InspectionsTesting

Test Levels

TestPurpose
Unit TestTests individual functions/modules independently, often by the developer during implementation
Integration TestTests interfaces between modules combined into one system (e.g., multiple functions inside one class working together)
System TestTests the whole system's functional & non-functional requirements in a realistic environment
Acceptance TestJudges whether the system is acceptable to the user — checks satisfaction, not defect-hunting
Lecture insight — a worked example ~29:23–30:55

Suppose the requirement is: "the product must communicate securely." To satisfy it, the design breaks this into: (1) a key-generation function, (2) selecting a protocol suite, (3) generating a hash. These design-level requirements get checked in the Integration Test. Whether the overall system is "secure when transmitting" is confirmed in the System Test. Going one level lower — e.g., "the key must be 128-bit" — that's checked at the Unit Test level, by testing the actual key-generation function and whatever sub-functions it calls.

Lecture insight — System Test vs. Acceptance Test ~34:41–35:30

Think of it this way: System Test = the developer testing on their own machine/lab environment ("does this work correctly and safely?"). Acceptance Test = testing the finished product in the real environment — e.g., installing the actual app, connecting it to real Wi-Fi, and confirming it behaves as intended in the field.

Key distinction: V-Model vs. Secure SDLC ~31:54–33:44

Both seem to test requirements/design/implementation — so what's different?

  • V-Model: implementation happens first, all the way through. Afterward, the code is divided and tested at different granularities: functions (Unit), design-level units (Integration), whole program (System), and real-environment run (Acceptance). The input to every test is ultimately code.
  • Secure SDLC: testing happens progressively, right after each phase — requirements are tested using the natural-language requirements themselves (or a formal specification derived from them), and design is tested against design models/diagrams (e.g., class diagrams) — not against code.

7. Spiral Model

Definition: Develops software incrementally by dividing functionality (like Prototype), but adds the concept of risk analysis.

Four repeated phases

  1. Planning – objectives, feature selection, constraints
  2. Risk Analysis – priorities of selected features and risk factors
  3. Development – build a prototype of the selected features
  4. Evaluation – assess the development results

Advantages

  • Early risk analysis lowers surprise risks → lower cancellation probability
  • Reflects user feedback → requirements well satisfied

Disadvantages

  • Repeated iterations may extend the timeline
  • More iterations = harder project management
  • Needs dedicated risk-management expertise
Lecture insight ~36:21–37:18

The Spiral model's defining feature is that it's the first model to explicitly prioritize which feature gets developed first — e.g., "we have limited time, so of features A, B, C, we build the essential one (A) first." Importantly, "risk" here does not mean "which feature has the most security vulnerabilities" — it refers to project-management risk: things that cause schedule delay or extra cost (e.g., developer turnover, requirement changes, client's financial trouble, staffing shortfalls, schedule/budget overruns).

8. Agile Model

Definition: Proposed in the late 1990s to shorten the Waterfall-based product cycle and respond more nimbly to customer needs.

Contrast with Waterfall: Waterfall produces one big outcome at the end; Agile repeats short Requirements → Design → Develop/Test → Deploy cycles, each producing a cumulative outcome.

Lecture insight ~38:17–39:55

Modern commercial product cycles (Microsoft was given as an example) typically run 6–12 months from requirements to release. Trying to follow a strict Waterfall process within such a short cycle is very impractical — that pressure is part of what drove the creation of Agile, which shares some spirit with Spiral but is optimized purely for speed. Key Terms

  • Verification: "Are we building the product right?" (process-focused, per-stage)
  • Validation: "Are we building the right product?" (final product-focused)
  • CMM(i): Capability Maturity Model (Integration) — proposed by Watts Humphrey
  • Secure SDLC: adds risk assessment, threat modeling, static analysis, security testing, and secure configuration to the standard SDLC — and tests each phase's own artifacts (requirements text/spec, design diagrams) rather than waiting for code
