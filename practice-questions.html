Week 2 — Software Development Life Cycle

Q1. Fill in: Verification asks "Are we building the product ____?" and Validation asks "Are we building the ____ product?" Then classify each activity as verification or validation: (a) a walkthrough of the design document against the requirements, (b) a customer demo of the finished sprint output, (c) an inspection of the test cases.

Show answer

Verification: "right"; Validation: "right" (are we building the right product). (a) Verification (reviews/walkthroughs/inspections of intermediate work products). (b) Validation (checks the actual software against business requirements). (c) Verification.

Q2. A developer intends y = x² but writes y = 2x. The test case is "x = 2 should give y = 4". Identify whether a fault, an error, and a failure occur. Repeat for the test "x = 1 should give y = 1".

Show answer

x = 2: fault yes (the code itself is wrong), error no (2·2 = 4, same as the intended 2² = 4), failure no. The fault stays hidden.

x = 1: fault yes, error yes (internal state is 2 instead of 1), failure yes (output 2 ≠ expected 1).

Takeaway: a fault can exist without being visible depending on the test input; this is one reason pair programming / broader test coverage matter.

Q3. Match each development phase on the left side of the V-model to the test that verifies it: Requirements analysis, Architecture design, Module design. Where do Acceptance tests fit?

Show answer

Requirements analysis ↔ System Test; Architecture design ↔ Integration Test; Module design ↔ Unit Test. The Acceptance Test comes after the System Test (top right of the V) and judges whether the user will accept the system (satisfaction, not defect hunting).

Q4. A requirement says "the product must communicate securely." The design splits it into key generation, protocol-suite selection, and hash generation. Which test checks each of: (a) "the key must be 128-bit", (b) these design-level functions working together, (c) "the whole system is secure when transmitting"? And how does System Test differ from Acceptance Test?

Show answer

(a) Unit test (the key-generation function itself). (b) Integration test. (c) System test.

System test = developer tests in their own/lab environment; Acceptance test = the finished product in the real environment (e.g., real app install, real Wi-Fi).

Q5. Choose the best-fitting model and give one reason: (a) requirements are stable and a well-documented, sequential process is needed; (b) requirements are unclear and users must see something quickly; (c) a large, high-risk project where early risk analysis matters; (d) very short release cycles and frequently changing requirements.

Show answer

(a) Waterfall (simple, systematic documentation, suits low requirement change). (b) Prototype (iterative requirement refinement with an executable prototype). (c) Spiral (risk analysis each loop, reduces chance of cancellation). (d) Agile (short sprints, quick response to change).

Q6. What does "risk" mean in the Spiral model? Give three examples.

Show answer

Project-management risk (things that cause schedule delay or extra cost), not "which feature has the most vulnerabilities." Examples: developer turnover, requirement changes after confirmation, the client's financial trouble, needing more manpower than expected, running out of time, going over budget. The Spiral model also prioritizes which feature to build first.

Q7. Give two disadvantages of Waterfall and two of Build & Fix.

Show answer

Waterfall: each stage must be finished before the next; deliverables must be near-perfect or errors propagate; users see nothing until late; fixing a late-found problem means revising earlier stages and costs grow exponentially.

Build & Fix: no fixed process or documented deliverables so it is hard to manage/maintain; team can't divide work effectively; progress is hard to see.

Q8. Scrum: who does what? Name the three roles and state what the Sprint Planning Meeting and the Daily Scrum each decide or share. Which is closest to a "kickoff meeting"?

Show answer

Scrum Master removes blockers and coordinates scrum events; Product Owner defines and prioritizes Product Backlog items and communicates with the team; Development Team builds.

Sprint Planning Meeting (kickoff-like): decide who does what, how, by when → produces the Sprint Backlog. Daily Scrum (~15 min, standing): share status (yesterday / today / blockers) against the already-set plan; update the board and burndown chart. Planning sets the rules; the Daily Scrum checks progress against them.

Q9. In V-model terms, what does the Sprint Review correspond to, and why? How long should it take at most?

Show answer

Validation — the team demos the working product to attendees (including the customer) and checks how well it meets requirements ("are we building the right product?"). Keep it to 4 hours or less.

Q10. Define Epic, User Story, Task, and Story Point with one example each (use a mobile finance app).

Show answer

Epic: large goal spanning several sprints (e.g., "users can manage money in the app"). User Story: one sticky-note requirement in user language (e.g., "a user can check account balance"). Task: concrete work for a story (e.g., call the balance API, design the screen). Story point: relative effort/time to complete a story.

Q11. Name any six of the twelve XP rules, and explain why pair programming helps.

Show answer

User Stories, Small Releases, System Metaphor, Collective Ownership, Coding Standard, Simple Design, Refactoring, Testing (TDD), Pair Programming, Continuous Integration, 40-hour Workweek (slide caps at 45 hrs), On-site Customer.

Pair programming: a second person reviews and catches logic that "works" from the author's view but is actually wrong (like the hidden-fault example in Q2).

Q12. What do the planned (dotted) and actual (solid) lines on a burndown chart show, and why does a project lead use it?

Show answer

Y-axis: remaining work (story points); X-axis: days in the sprint. Dotted = planned remaining work per day; solid = actual remaining work. The chart goes down over time. A lead (who isn't coding) can see who finished early and reassign effort, and see whether the sprint is on track.

Week 3 — MS-SDL

Q1. Which of these products must follow SDL? (a) a mail server used across enterprises, (b) a personal offline calculator app, (c) a medical app storing patient data, (d) a browser, (e) software that auto-downloads updates.

Show answer

Must follow SDL: (a), (c) (PII), (d) (sends/receives data over the internet), (e). (b) is not mandatory (SDL is still recommended for all software). Mandatory cases: enterprise-common products, regularly handles PII, regularly sends/receives data over the internet, automatically downloads updates.

Q2. Which secure design principle is illustrated? (a) A new account has no permissions until explicitly granted. (b) A backup job runs only with the rights it needs. (c) Every file read goes through the same permission check. (d) The algorithm is public; only the key is secret. (e) Both a firewall and application-level authentication protect the same service. (f) Each process writes to its own log file instead of a shared one.

Show answer

(a) Fail-safe Defaults; (b) Least Privilege; (c) Complete Mediation; (d) Open Design (Kerckhoffs's Principle); (e) Defense in Depth; (f) Least Common Mechanism.

Q3. State the three Attack Surface Reduction steps and give the IIS example for step 1 and the Sasser example for step 2.

Show answer

1) Is the feature really necessary? (if not ~80% of users need it, default it to off) — IIS 6.0 on Windows Server 2003 isn't installed by default, whereas IIS 5.0 on Windows 2000 was. 2) Who needs access, and from where? (remote anonymous is far riskier than local admin) — Server 2003 wasn't affected by Sasser because the target area needed an admin physically at the keyboard. 3) Reduce privileges (run in non-admin mode; services under low-risk accounts, not Local System).

Q4. What is a Bug Bar, and which bug severities must be fixed before release under SDL?

Show answer

The Bug Bar defines the nature of a threat and its risk level, set at project start so everyone knows what must be fixed, mitigated, or left. SDL requires fixing Critical, Important, and Moderate security/privacy bugs before release.

Q5. A threat is scored D=8, R=6, E=7, A=9, Discoverability=4 under DREAD. What is its average? What does each letter stand for? Why did Microsoft stop using DREAD (2008)?

Show answer

Sum = 34, average = 6.8. Damage potential, Reproducibility, Exploitability, Affected users, Discoverability.

Dropped because results were inconsistent between evaluators and too subjective/qualitative; Microsoft now uses Bug Bar information from the MSRC.

Q6. Draw the DFD element type for each: (a) an external payment server, (b) the login program, (c) the SQL database's disk storage, (d) the DBMS software, (e) the arrow carrying the password, (f) the boundary between the user's app and the OS.

Show answer

(a) External entity; (b) Process; (c) Data store; (d) Process (the DBMS is software); (e) Data flow; (f) Trust boundary.

Q7. Name the 2023 four mitigation (risk-treatment) types and give a one-line example of each.

Show answer

Mitigation (lower the risk, e.g., add encryption); Transfer (shift to another party, e.g., insurance); Acceptance (risk low enough to accept); Elimination (remove the feature that causes it). The 2011 list had three: warn the user, remove the feature, mitigate technically.

Q8. In the SDL Process Maturity Model, what does each rating 0–4 mean for a threat model?

Show answer

0 = no threat model (unacceptable). 1 = outdated (design differs a lot, document over 12 months old). 2 = OK (minimum: DFD/asset list, at least one threat per asset, mitigations for Level 1/2/3 threats). 3 = Good (meets OK; anonymous/authenticated/local/remote users in DFD; all S/T/I/E threats mitigated and classified; penetration-tested). 4 = Excellent (all STRIDE threats identified with mitigations/external security notes; mitigation confirmed per threat; customer-facing safe-use docs planned).

Q9. What is Attack Surface Analysis vs Attack Surface Reduction? What is "Psychological Acceptability," and what real-world lesson did Microsoft learn (Windows XP SP2)?

Show answer

ASA identifies the entry points (code, interfaces, services, protocols) an attacker can use and who can reach them; ASR shrinks that surface (less code on by default, fewer users/IDs, lower privileges). Psychological Acceptability: security features must be easy to use or users will turn them off; XP SP2 balanced security, usability, and backward compatibility.

Week 4 — STRIDE & LINDDUN

Q1. Fill the table: for each STRIDE threat, give the violated security property. S, T, R, I, D, E.

Show answer

Spoofing → Authentication; Tampering → Integrity; Repudiation → Non-repudiation; Information disclosure → Confidentiality; Denial of service → Availability; Elevation of privilege → Authorization.

Q2. A DFD has 2 external entities, 2 processes, 1 data store (no log data), and 4 data flows. Using STRIDE-per-element, how many theoretical threats are there? Show the working.

Show answer

External entity: 2 threats (S, R) × 2 = 4. Process: 6 (S,T,R,I,D,E) × 2 = 12. Data store: 3 (T, I, D; R only if it stores logs) × 1 = 3. Data flow: 3 (T, I, D) × 4 = 12. Total = 31. (If the store holds log data, +1 for repudiation = 32.)

Q3. The real system has functions A, B, C, D, E where A calls B or C or D, then E, which calls A again. Student 1's model has only A, B, C, D. Student 2 draws A→B→E→A with all the functions present. Which student broke completeness, which broke soundness, and why?

Show answer

Student 1 broke completeness (a real function is missing from the model). Student 2 broke soundness (all functions present, but the call structure/meaning differs from the real system).

Q4. Why does the lecturer say to analyze data flows that cross the trust boundary in more detail? Can you skip threats inside the boundary?

Show answer

Real attacks start at external interfaces (SQL injection into a login process, brute force, social engineering), so those flows are where attacks concentrate. Inside the boundary you may assume it's safe (e.g., strictly runtime-monitored) and skip those threats as a documented assumption (MS-SDL security assumptions) — or assume it is not safe since internal threats can chain with external attacks.

Q5. Match: CVE, CWE, CAPEC, MITRE ATT&CK — (a) weakness types, (b) tactics and techniques from real attacks, (c) flaws in specific products, (d) attack patterns for exploiting a weakness. What is CPE used for?

Show answer

CVE = (c); CWE = (a); CAPEC = (d); ATT&CK = (b). CPE (product enumeration, attached to CVE entries) tells which product/product family a vulnerability affects, so you can judge whether it's relevant to your target.

Q6. Given the abstract threat "attacker spoofs a legitimate client" and this attack library: AL-V-3 (fake GUI captures credentials), AL-W-3 (capture an ID/password packet and replay it), AL-P-2 (record voice and replay it), AL-V-5 (phishing). The system uses voice login only. Write the concrete spoofing threats and say which entries you drop.

Show answer

Keep AL-P-2 (replay a recorded voice to impersonate the user) and AL-V-5 (phishing/social engineering to get secrets or trick the user). Drop AL-V-3 (fake GUI for typed credentials) and AL-W-3 (ID/password packet replay) since the system doesn't use typed credentials. What you can use from the library depends on what exactly you're modeling.

Q7. A STRIDE-per-element threat has no matching entry in your (well-maintained) attack library. Do you delete it? Why or why not?

Show answer

Not automatically. Missing library info doesn't prove it is impossible: zero-days or unknown vulnerabilities may exist, and future resources (e.g., AI/compute) could make it exploitable. Treat it as a potential security threat and carry it into scenario/attack-tree work as needed. (The slide example drops such threats; the lecturer's nuance is the safer answer.)

Q8. Goal: "steal the customer's login." They need the ID AND the password. The ID can be obtained by packet sniffing OR social engineering; the password can be obtained by packet sniffing OR brute force. Draw the attack tree in text and mark AND/OR. Costs to block each leaf: sniff-ID 5, social-engineer-ID 3, sniff-password 5, brute-force-password 4. What is the cheapest way to neutralize the whole goal?

Show answer

Tree: Root "steal login" = AND( "get ID" = OR(sniff ID, social-engineer ID), "get password" = OR(sniff PW, brute-force PW) ).

AND rule: blocking one child of the AND kills the root. OR rule: to kill an OR child you must block all its children. Cost to kill "get ID" = 5 + 3 = 8; cost to kill "get password" = 5 + 4 = 9. Cheapest = block the ID branch (8), also weighing reuse of existing security functions.

Q9. In an attack tree, what are the root, a leaf, a parent, and a child? How is AND drawn and how is OR drawn? What is a "sequential AND"?

Show answer

Root = attacker's final goal; leaf = a detailed method; parent = goal, child = a condition/method to reach it. AND = arc across the edges (or a line joining them); OR = no mark. Sequential AND = AND with an arrow: one condition must be satisfied before the other (not required for this course).

Q10. Compare STRIDE-per-element and STRIDE-per-interaction (pros, cons). Which one does MS-TMT effectively use, and how does it feel as easy as per-element?

Show answer

Per-element: fast and simple, but abstract and misses threats from interactions. Per-interaction: more concrete (e.g., Bluetooth beacon spoofing) but depends on analyst knowledge, slower, more complex (brainstorming). MS-TMT uses per-interaction: analysts' knowledge was turned into patterns applied automatically, so it looks as easy as per-element.

Q11. Write the seven LINDDUN threats and the property each violates. Which ones apply to an external entity under the per-element table?

Show answer

Linkability (unlinkability); Identifiability (anonymity/pseudonymity); Non-repudiation (plausible deniability); Detectability (undetectability/unobservability); information Disclosure (confidentiality); content Unawareness (content awareness); policy & consent Non-compliance (compliance). External entity: L, I, U. Process, data flow, and data store: L, I, N, D, D, and Non-compliance (not U).

Q12. Why is "Non-repudiation" a threat in LINDDUN, while "Repudiation" is a threat in STRIDE?

Show answer

STRIDE is about security: the attacker denies having done something (a threat to accountability). LINDDUN is about privacy: if every action is recorded so the subject cannot deny it, plausible deniability is lost, which harms privacy.

Q13. List the seven required fields of a LINDDUN misuse case, and the five LINDDUN process steps.

Show answer

Misuse case: summary; assets, stakeholders and threats; primary misactor; basic flow; alternative flows; trigger; preconditions. Process: create DFD → threat enumeration (per-element + filtering, then threat trees) → misuse case → risk assessment (DREAD/OCTAVE) → remediation.

Q14. What does the Attack Library step contribute, and why is it done continuously rather than once?

Show answer

It makes abstract STRIDE threats concrete (adds the "how"), so attack trees and countermeasures are accurate rather than aimed at threats that can't happen. It's time-consuming and vulnerabilities are constantly updated, so it must be maintained throughout the threat-modeling process.

Week 5 — SPARTA

Q1. Give two problems of manual threat modeling and how automation addresses each.

Show answer

(1) Costly, and earlier results are almost impossible to reuse when the system is improved → automated modeling lets you reuse results and re-evaluate the improved design. (2) Inconsistent records between analysts make it hard to trace which solution mitigates which threat → a catalog that forces all required information gives traceability between threats and solutions.

Q2. Give three reasons threat modeling must be repeated rather than done once.

Show answer

New vulnerabilities appear during development; a countermeasure's effectiveness changes over time (e.g., 10→5 may become 10→8 with faster CPUs/AI); and a countermeasure itself changes the attack surface and can become a new attack target. Repeat until no threat is exploitable within realistic time/cost.

Q3. State two limitations of MS-TMT's solution modeling and the 20% finding.

Show answer

Solution details can't be expressed, and what can be expressed is biased toward encryption (made abstract so non-security developers can use it). Entering what little solution info exists removes about 20% of threats early, but you can't tell which info caused the removal, can't compare solutions' efficiency, and the DFD itself doesn't hold the solution info.

Q4. What were SPARTA's two core ideas, and what is the difference from MS-TMT?

Show answer

(1) Extend the DFD metamodel to hold threat and solution information (Role, RoleBinding, Solution, CounterMeasure, ThreatType). (2) Define threat and solution patterns. Unlike MS-TMT, solutions are applied directly in the DFD model and tracked to the threats they mitigate.

Q5. Describe the tracing chain from a DFD element to a threat in SPARTA, using SecurePipe as an example.

Show answer

DFD element → RoleBinding to a Role (Client/Server/Flow) → the Solution (SecurePipe) that defines those roles → its CounterMeasures (AuthN, MAC, Enc) → the ThreatTypes mitigated (Spoofing, Tampering, Information Disclosure). Roles are based on function (requester = Client, responder = Server), not on names.

Q6. Classify as false negative, false positive, or duplicate: (a) only DB-itself threats considered, so threats from DB query requests are missed; (b) a mapping table generates a threat that can't occur in the real environment; (c) one tampering threat is recorded at the data flow, the sending process, and the receiving process.

Show answer

(a) False negative; (b) false positive; (c) duplicate.

Q7. Name the five kinds of information SPARTA uses for threat elicitation, and explain what Controlled Natural Language (CNL) is used for.

Show answer

Information (data types), Operation, Countermeasure, Attack, Action. CNL = natural language written in a fixed template; weakness descriptions (e.g., CWE) are first converted into the five-part template, then modeled as a VIATRA pattern, so that different people don't define inconsistent or erroneous patterns.

Q8. Describe the Stored XSS pattern in terms of DFD elements.

Show answer

External entity 1 (attacker) → process(es) → data store (shared) → process(es) → external entity 2 (normal user), with no tampering mitigation on the attacker's flow. The two entities differ; the processes may be the same; the data store must be common.

Q9. Write the SPARTA risk formulas, then compute: PoA = 0.5, CF = 4, TC = 7, S = 5, CB = 0, RP = 0.5, AV = 1000, DTS = 2, NR = 10, DST = 3, NDS = 5.

Show answer

Risk = LEF × LM; LEF = TEF × V × RP; TEF = PoA × CF; V = Max(CD, CB); CD = 1 if TC ≥ S else 0; LM = AV + PV; PV = DTS × NR × DST × NDS.

TEF = 0.5 × 4 = 2. CD: TC(7) ≥ S(5) → 1; V = Max(1, 0) = 1. LEF = 2 × 1 × 0.5 = 1. PV = 2 × 10 × 3 × 5 = 300; LM = 1000 + 300 = 1300. Risk = 1 × 1300 = 1300. If S were 9, CD = 0, V = 0, so Risk = 0.

Q10. What is Monte Carlo simulation, and how does SPARTA use it?

Show answer

Repeatedly generating random values from a probability model, simulating with them, and finding the probability distribution of the answer. SPARTA models inputs (S, TC, CF, PoA, ...) as distributions and combines them up the risk tree to get a distribution of risk, which it uses to prioritize threats and show how much risk a solution removes.

Mini case study (combine Weeks 3–5)

A smart-door-lock app: the Owner (phone) sends an unlock command to the Cloud server (process), which checks the Accounts DB (data store) and relays the command to the Lock (device, outside your scope). The attacker is on the internet. The trust boundary separates the phone from the cloud.

(a) List the DFD elements and their types. (b) Which flows deserve the most attention, and why? (c) Write two concrete spoofing/tampering threats on the phone→cloud flow if the attack library says: "T1: replay of captured unlock packets" and "T2: default admin credentials". (d) Draw an attack tree for the goal "unlock the door without the owner". (e) Which mitigation types apply to each leaf?

Show model answer

(a) External entities: Owner, Lock (outside the analysis scope, depending on what you analyze; if the Lock is in scope, make it a process). Processes: Cloud server (and the DBMS if drawn separately). Data store: Accounts DB. Data flows: Owner→Cloud (unlock request), Cloud→DB (query), DB→Cloud (result), Cloud→Lock (command). Trust boundary between the phone and the cloud.

(b) The Owner→Cloud flow crosses the trust boundary and faces the internet, so attacks concentrate there; analyze it in more detail (and the Cloud→Lock flow if it crosses another boundary).

(c) Spoofing: attacker replays a captured unlock packet to impersonate the owner (T1). Elevation of privilege/spoofing: attacker logs in with default admin credentials (T2). Tampering: modify the unlock request in transit if the channel is unencrypted (potential threat even without a matching library entry).

(d) Root: unlock without owner = OR( A: send a forged unlock command = AND(obtain a valid command — via replay OR default credentials; reach the cloud interface), B: tamper with the Cloud→Lock command in transit ). Draw AND with an arc, OR with no mark.

(e) Replay → mitigate (nonces/timestamps, encrypted channel); default credentials → eliminate the default account/force change (mitigation or elimination); tampering in transit → mitigate (MAC/encryption). Accepting is only appropriate for low risks; transfer is e.g. insurance for residual risk.
