1. Background

What is MS-SDL?

MS-SDL (Microsoft Security Development Lifecycle): a 13-stage software development process designed by Microsoft to improve software security and privacy.

  • Goals: reduce the number of security vulnerabilities and privacy issues; reduce the risk posed by any vulnerabilities that remain.
  • Audience: software development teams, development-process managers, and software designers/architects.

SDL evolution

  • The security landscape evolves quickly, so a security-focused development process can't stay static.
  • Microsoft updates and revises the SDL twice a year (January and July).
  • The process is designed to only incorporate requirements that are demonstrably effective at improving software security.

Recommendations vs. Requirements

TermMeaning
RecommendationNot mandatory, but good practice for a team improving software security
RequirementMust be followed going forward for software security

If a proposed change becomes a requirement, it must include a way to verify compliance, and the team must identify who will test the proposed change and provide feedback.

2. Why SDL is Necessary

  • SDL was developed to accommodate customers' demand for secure software and to preserve company trustworthiness/reputation.

The cost problem of security updates

  • Major software vendors find it more cost-effective to build in trustworthiness early in development than to patch security issues later.
  • Why Microsoft adopted SDL: to build more secure software and reduce customer pain — SDL is credited with a 50%+ reduction in vulnerabilities.

MS-SDL Overview

  • Microsoft's own MS-SDL process runs on a roughly yearly (12-month) cycle, suited to its own development environment.
  • Not suitable for product lines with a relatively short (4–5 month) development cycle.
  • Follows "Shift Left" and "Continuous Improvement" principles well — roles are clearly divided between the development team and the security team throughout the process.
High-level flow (exam-relevant)

Training → Requirements → Design → Implementation → Verification (Testing) → Release → Response, repeated on a 12-month cycle, with the overarching goal of reducing vulnerabilities and mitigating risk levels throughout.

3. The 13 Stages of MS-SDL (Overview)

  1. Training & Awareness
  2. Project Inception (Requirements)
  3. Define & Follow Design Best Practices
  4. Product Risk Assessment
  5. Risk Analysis
  6. Create Security Documentation, Tools, and Best Practices for Customers
  7. Secure Coding Policies
  8. Secure Testing Policies
  9. Security Push
  10. Final Security Review (FSR)
  11. Security Response Plan
  12. Product Release
  13. Execute the Security Response

Note: this lecture covers Stages 1–5 in detail; Stages 6–13 will be covered in later sessions.

Stage 1Training & Awareness

Overview

Why SDL succeeded at reducing vulnerabilities in Microsoft software:

  • Executive/management support
  • Training and awareness
  • Engineers need to know about software security — potential vulnerability info, security-relevant design and testing approaches, etc.
  • Security means understanding what's required to build and deliver secure features — how defense mechanisms and cryptographic algorithms work (e.g., the internals of the Java Sandbox or Microsoft .NET CLR, DES, RSA), and how to respond to the limitations of those mechanisms/algorithms (e.g., DES's key size limitation).

History of Microsoft Security Training

Early internal training focus

Early internal technical training focused on how security technologies work, not just how to build secure software:

  • Common reasons security bugs go unfixed
  • Design problems: open ports, improperly stored keys, bypassing authentication/authorization schemes
  • Understanding software threats — BOF, XSS, SQL Injection, and other threats from bad coding

Other detailed topics covered: software engineering principles, lessons from past projects, software architecture, testing methods, transactional technology, reliability, scalability, understanding future tech directions, various technologies (XML, ASP, SOAP), programming languages, interface design, accessibility.

"The Basics" awareness program

  • Microsoft launched an awareness program called "The Basics of Secure Software Design, Development, and Test".
  • Purpose: raise awareness of security issues, explain why security matters, and help people realize how little they actually know about security.
  • All Microsoft employees must attend security training at least once a year.

Training delivery methods

  • Live training sessions — effective, but hard to scale across thousands of employees; expensive.
  • Recorded live sessions — stored internally so employees can access them anytime.
  • Attendance/compliance tracking: for a Microsoft product to comply with SDL, every employee must have completed security training within the last year — attendance is automatically logged in a database.

Knowledge measurement

  • Easiest method: after an online training session, ask multiple-choice questions based on the material — correct answer → move to next material; incorrect → shown the right answer, then continue.
  • In-house training requirement: to set a minimum security baseline, every engineering manager must attend training sessions.

Stage 2Project Inception

Overview

The stage where you determine whether the product is subject to SDL.

  • All software can benefit from the SDL process, and managers are always "recommended" to follow it.
Mandatory SDL applicability

The following product types must follow SDL:

  • Products commonly used or deployed within an enterprise (e.g., email and data servers)
  • Products that regularly store, process, or transmit PII (Personally Identifiable Information) — e.g., financial, medical, or other sensitive customer info
  • Products that regularly send/receive data over the internet — e.g., web browsers, email clients, mobile systems
  • Products that automatically download updates

Task 1 — Appoint a Security Advisor

  • Nominate a security advisor to guide the development team through SDL toward a successful FSR.
  • If the company has a security team or Security Quality team, it's best to appoint someone from that team.

Security Advisor's role

  • Point of contact between the dev team and security team
  • Hosts the SDL kickoff meeting for the dev team
  • Reviews the design and threat model with the dev team
  • Analyzes and classifies security/privacy-related bugs
  • Acts as a security "sounding board" — resolving security/privacy questions and ideas
  • Prepares the dev team for FSR
  • Works with the reactive security team afterward

Task 2 — Build a Security Leadership Team

  • Microsoft has a central project management team that leads day-to-day communication, scheduling, and feature coordination — this team also owns security leadership for the project.

Security Leadership Team's role

  • Regularly emails the dev team about the number of security/privacy bugs
  • Communicates updates to security/privacy policy

Task 3 — Ensure the Bug-Tracking Process Includes Security & Privacy Fields

  • Tracking security/privacy bugs correctly and consistently in the bug database is critical.

Required SDL bug-tracking fields

FieldPredefined values
Security/Privacy Bug EffectNot a security bug, Spoofing, Tampering, Information Disclosure, Privacy, Denial of Service, Elevation of Privilege, Attack Surface Reduction
Security/Privacy Bug CauseNot a security bug, Buffer Overflow/Underflow, Arithmetic Error (e.g., integer overflow), SQL/Script Injection, Directory Traversal, Race Condition, XSS, Cryptographic weakness, Weak Authentication, Weak Authorization/improper ACL, Ineffective secret hiding, Resource exhaustion, Missing/incorrect error messages, etc.

Task 4 — Determine the "Bug Bar"

  • The Bug Bar defines the nature of a threat and its corresponding risk level.
  • At the start of the project, decide which bug types (including security/privacy bugs) will be fixed within the development lifecycle.
  • Fixing the bar in advance reduces confusion about what must be fixed, what should be mitigated, and what can be left unfixed.
  • SDL requires that Critical, Important, and Moderate-level security/privacy bugs be fixed before release.

Stage 3Define & Follow Best Practices (Design Requirements)

What is a "Best Practice"?

A problem-solving method or successful solution for consistently and effectively achieving a goal. The software industry has plenty of secure coding best practices, but is relatively lacking on secure design. This stage's goal is to provide principles and best practices for applying secure design to software development.

Framing best practices to engineers

When giving engineers guidance to reach a goal, it's counterproductive to just say "don't do the wrong/bad thing." Instead, say "do it this way" — if engineers are given a clear method, they'll be able to comply with security/privacy policy without friction.

Key definitions

  • Attack surface: the internal entry points or attack vectors of software that an unauthorized user (attacker) could use to access or extract data from a system. Example: a network socket an application opens for communication.
  • Threat modeling: identifying possible threats to a system and determining appropriate mitigations — the activity of identifying every possible vulnerability/risk.

Task 1 — Define Secure Design Principles ("Security Hygiene")

A set of best practices focused on the overall security hygiene of a system/application:

PrincipleMeaning
Economy of Mechanism Keep design and code small and simple — smaller code has less that can go wrong.
Fail-safe Defaults Unless a subject is explicitly granted access to an object, access should be denied by default (unspecified access/privilege/security attributes = denied). Also: if a subject can't complete its operation, any security-state changes it made should be rolled back before termination.
Complete Mediation Validate every access to every protected object — every event in the system must be monitored by a security function.
Open Design "Security through obscurity" is rejected — design should not rely on secrecy. Even if the design falls into enemy hands, there should be no advantage gained. Related: Kerckhoffs's Principle — a cryptosystem's security should depend on keeping the key secret, not the algorithm.
Separation of Privilege Grant different permissions for different operations (e.g., Read / Write / Execute separately).
Least Privilege Grant only the minimum privilege necessary to perform a task.
Least Common Mechanism Minimize routines that use shared resources (files, shared memory/variables). E.g., local variables are safer/more stable than global variables; separate files per process are easier to manage safely than one shared file across processes.
Psychological Acceptability Security features must also be easy to use — an easy program beats a hard one, and this applies to security features too. Requires a lot of experience and skill to get right.
Design by Contract (Eiffel) Specifies exact usage conditions/behavior of classes/routines via precondition (must hold before a component is called), postcondition (guaranteed after execution if precondition held), and class/object invariant (must hold continuously). Microsoft extended this concept to .NET for runtime/dev-time testing (see Microsoft's CodeContracts project).
Not Bolt-on, Built-in Security and privacy must be considered during the design stage — deferring them until after other functionality is built ("bolting them on") is not an acceptable option.
Defense in Depth Don't rely on a single security mechanism. Apply multiple independent/complementary security controls in layers, so that if one defense fails or is bypassed, another still blocks or limits the attack's impact.
Effective Logging Record security-relevant events in an identifiable form, so breaches, policy violations, and abnormal behavior can be detected, and root cause/sequence of events can be traced after an incident.
Real-world caution — Psychological Acceptability

Reflecting user psychology correctly is hard in practice. If a security feature gets in the user's way too much or is too hard to use, users will simply disable it — exposing the system to more threats. Because of this, when developing Windows XP Service Pack 2, Microsoft paid close attention to balancing Security, Usability, and Backward Compatibility.

Task 2 — Attack Surface Analysis (ASA)

  • Anything a user can access — code, interfaces, services, protocols — can be part of the attack surface. Example: code running behind an open socket.
  • ASA is closely linked to threat modeling — it's a core component of it, dealing with the system's entry points and the trust level able to access each one.

Task 3 — Attack Surface Reduction (ASR)

Since every piece of code has at least one vulnerability, ASR provides a middle ground between perfect security and unmitigated risk:

  • Reduce the amount of code that runs by default
  • Limit the range of users who can access the code
  • Limit the range of IDs (e.g., system user list) that can access the code
  • Limit the execution privileges of the code

ASR — Step 1: Is this feature really necessary?

  • Ask, for each product feature: "would at least 80% of users need this feature/characteristic?"
  • If not required → the feature should default to disabled.
  • Disabling a feature by default does not mean shipping a lower-quality product.
Real example

Windows Server 2003's IIS 6.0 is set to not install by default, whereas Windows 2000's IIS 5.0 was installed by default — a direct application of this principle after learning from past incidents.

ASR — Step 2: Who needs access, and from where?

  • Determines who can access the code, and how far that access reaches (Distance, Trust level).
  • Remote Anonymous access is relatively far more dangerous than Local Admin access.
Real example — Sasser worm

Windows Server 2003 users were unaffected by the Sasser worm, because the worm's attack target was an area only accessible to an administrator physically at the keyboard.

  • Firewalls can restrict a lot of network-level access, but you must still plan a defense layer for the case where the firewall is disabled.

ASR — Step 3: Reduce privileges

  • Primary targets: Unix daemon processes and Windows Services — long-running, typically high-privilege.
  • Code running with more privilege than necessary is a direct path to system compromise.
  • Privilege should be assessed on two axes: "which account is this associated with?" and "what privileges does that account's group have?"
  • Create accounts with only the privileges the user needs, or run services under well-known accounts, and revoke unneeded privileges at program startup (e.g., using the AdjustTokenPrivileges function).
  • Programs should launch in non-administrator mode by default to avoid these risks.
  • Services should run under lower-risk accounts rather than the Local System account.
Rule of thumb

Only the administrative process should run with high privilege — it's also good practice to split a program's internal processes based on the privilege level each actually needs.

Stage 4Product Risk Assessment

Overview

  • Bigger threat → more design/development cost. This stage estimates the cost needed to carry out security activities during development.

Items to be determined at this stage

  • Which parts of the project need threat modeling before release
  • Which parts need a security design review
  • Which parts need penetration testing
  • The scope of fuzz testing requirements

Task 1 — Security Risk Assessment

  • Performed to determine the system's vulnerability level. A short set of questions makes the assessment easier, e.g.:
CategorySample question
Software setupWhat operating system(s) will the software be installed on?
Attack surfaceIs the feature installed by default when the software is installed?
Mobile code (scripts)Does it include ActiveX controls?
Security-related featuresDoes the program implement an authentication mechanism?
GeneralIs this the product's first version? If not, what's different from the previous version?

Answers in each category help the security team decide the scope and depth of analysis needed.

Task 2 — Privacy Impact Assessment

  • Helps provide differentiated privacy protection ordered by how sensitive/high-impact the data is.

Stage 5Risk Analysis

Overview

Very similar work to threat modeling:

  1. Define usage scenarios
  2. Gather a list of external dependencies
  3. Define security assumptions
  4. Write external security notes
  5. Create a Data Flow Diagram (DFD)
  6. Determine threat types
  7. Identify threats to the system
  8. Determine risk
  9. Plan mitigations

What is Threat Modeling?

  • A process for identifying, enumerating, and prioritizing potential threats — such as structural vulnerabilities — from the perspective of a hypothetical attacker.
  • Accurately maps the application's attack surface
  • Assigns risk to various threats
  • Drives the risk-mitigation process
Why threat modeling is valuable

Because it happens early in the development lifecycle, threat modeling can catch security design problems at a relatively low cost compared to fixing them later.

1. Define Usage Scenarios (Use Case Diagram)

  • An ordered description of how a user goes through using the product — "who does what?"

2. Gather a List of External Dependencies

  • Identify external elements that the analysis target depends on, e.g.:
  • Info about the devices running an SNS 2.0 app (device type, OS version, etc.)
  • Info about the DB where personal data is stored
  • Other web servers
  • The OS running on the server, etc.

3. Define Security Assumptions

Why this matters

Incorrect security assumptions about the environment where an application runs can make the whole application unstable.

  • If the system defaults to using encryption, what counts as a "safe" cryptographic algorithm?
  • Will third-party components be trusted?
  • If the app stores crypto keys, will it assume the underlying OS correctly protects those keys (a design requirement that relies on the OS)?

Write External Security Notes

  • Based on dependencies and assumptions, documents security-relevant info usable to protect the system, or documents the security effect of enabling certain features — for the benefit of system users.

5. Create a Data Flow Diagram (DFD)

Built from 5 elements that together capture all data flow for the analysis target:

ElementDefinitionExample
External EntityAn entity operating outside the scope of the analysis targetPeople, other systems, websites
ProcessA function inside the codeExecutables, assemblies, COM components
Data FlowData being transmittedFunction calls
Data StoreA system where data is storedFiles, databases, registry keys
Trust BoundaryA boundary where entities of different trust/permission levels operateUser app ↔ OS boundary
  • Also known as the "threat model diagram", since it's primarily used for threat modeling.
  • Each element gets an identifier for clear communication (e.g., P1 Login, E1 Developer, F1 Account info, S1 DB).
  • A real system's DFD often has ~10–150 elements and can get complex. To reduce complexity, use bidirectional arrows where possible — but use unidirectional arrows when the data flowing each way differs.

DFD granularity levels

LayerMicrosoft's minimum recommendation
Layer 0 (System layer / Context diagram)Required for all systems — shows major system parts
Layer 1 (Process layer / DFD level 0)Required for most systems — adds diagrams for each system part
Layer 2 (Subprocess layer / DFD level 1)Required for highly sensitive systems — adds diagrams for subparts
Layer 3 (Lower layer / DFD level 2)Required for critical or kernel-level systems — a diagram for every process

Which level(s) are actually produced depends flexibly on the SDL project schedule.

ThreatViolated PropertyDefinitionTarget
SpoofingAuthenticationPretending to be someone/something elseProcess, external IT entity, person
TamperingIntegrityModifying something on disk, network, or in memoryProcess, data store, data flow
RepudiationNon-repudiationClaiming you did nothing / bear no responsibilityProcess

7. Identify Threats to the System

  • Map each DFD element against the STRIDE threat categories to identify possible attacks against the system.
  • Because each component is analyzed individually, this takes less time and keeps the analysis process simple.

8. Risk Assessment

Historically, many companies used a numeric formula:

Classic formula

Risk = Chance of Attack × Damage Potential

Microsoft made this more concrete with the DREAD model.

DREAD

A methodology for scoring the severity of an identified threat, to help prioritize mitigation. Each risk factor is scored 1–10, then averaged.

FactorQuestion0 (low)5 (mid)10 (high)
Damage PotentialHow much does damage spread if attacked?No spreadSpreads to individual user dataSystem or data is fully destroyed
ReproducibilityHow often/easily can the attack be attempted?Very hard/impossible; needs admin-level accessNeeds 1–2 steps; needs a privileged user-level accountA web browser alone is enough; no privilege needed
ExploitabilityHow much effort does the attack require?Needs advanced programming/networking knowledgeNeeds to understand/use info that's already public onlineBasic web browser functionality is enough
Affected UsersHow many users could be affected by the same attack?Single user or noneSome users (not all)All users
DiscoverabilityHow likely is the vulnerability to be found?Very hard; requires source code / admin-only screen accessDetectable via guessing or network sniffingRegistered on a public domain (e.g., Shodan) = 9; discoverable with just a browser = 10
Why Microsoft dropped DREAD

Critics pointed out that DREAD (like earlier risk-assessment methods) could produce inconsistent results depending on the evaluator, and was seen as too subjective/qualitative. Because of this, Microsoft stopped using DREAD in 2008 and now performs risk assessment based on Bug Bar information provided by the Microsoft Security Response Center (MSRC).

9. Mitigation Planning

The set of mitigation categories has expanded over time from 3 to 4:

2011 version (3 types)2023 version (4 types)
Warn the userRisk Mitigation: reduce the threat's risk level via various measures
Remove the feature causing the threatRisk Transfer: shift responsibility for the risk to another organization (e.g., an insurer)
Mitigate the threat via technical measuresRisk Acceptance: accept the risk because its level is low enough
—Risk Elimination: remove the system feature that could cause the threat, eliminating the risk entirely

Evaluation Criteria for the Risk Analysis Process — SDL Process Maturity Model

RatingComments
No threat model (0)No threat model exists — unacceptable, since it implies no threats were considered
No threat model (1)An outdated threat model version exists; the current design differs significantly from the modeled design; the document is over 12 months old
OK (2) — minimum threat modelA DFD (or a list of: assets [processes, data stores, data flows, external entities], users, trust boundaries [machine-to-machine, kernel/user, elevated]) exists; at least one threat is detailed per product asset; mitigations are provided for all Level 1/2/3 threats
Good (3) — penetration-tested component, using the latest modelMeets all "OK" criteria; anonymous, authenticated, local, and remote users are all shown in the DFD; all S/T/I/E threats are mitigated and identified/classified as accepted
Excellent (4) — penetration-tested componentMeets all "Good" criteria; all STRIDE threats are identified along with mitigations, external security notes, or dependency confirmation; a mitigation method is confirmed for each threat; external security notes include a plan for customer-facing docs explaining safe usage and trade-offs
