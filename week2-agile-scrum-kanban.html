1. Agile Model — Introduction

Definition: Proposed in the late 1990s to shorten Waterfall-based product cycles and respond more nimbly to customer needs, solving problems as they come up.

Agile Manifesto values (vs. traditional approaches)

  • Individuals & interactions over processes and tools
  • Working software over comprehensive documentation
  • Customer collaboration over contract negotiation
  • Responding to change over following a plan

Regular meetings between the team and the customer let changes be reflected immediately. A 2018 industry survey found 97% of respondents' organizations report practicing some Agile method.

Sub-models under Agile

  • Scrum — 3 roles (Scrum Master, Product Owner, Scrum Team) work in sprints of ≤4 weeks.
  • Kanban — originally a Toyota manufacturing method; applied to software engineering around 2004; a Microsoft project used it in 2010; 5 core principles.
  • Extreme Programming (XP) — a rule set (12 rules) layered on existing software engineering to react even faster to changing requirements.
Lecture insight — why Agile exists ~00:00–01:32

Agile is less a rigid "process" and more a philosophy: "respond nimbly to whatever comes up." The kind of sudden problem Agile is built to absorb includes things like a new foreign regulation suddenly requiring a certain development approach, or a newly disclosed vulnerability — the classic example is Heartbleed, which suddenly broke a huge amount of existing TLS communication and leaked information. When something like that hits mid-project, you need a way to fold the fix into your current development as fast as possible — that's exactly what Agile was designed for.

Lecture insight — development-cycle comparison ~15:48–18:44

Compared to other SDLC models, Agile's sprint length is remarkably short:

  • Waterfall: heavily used by large conglomerates and especially the defense industry, where the whole process — software included — runs on a roughly yearly cycle.
  • Automotive industry: typically follows the V-model; a new car's development can take many months to a full year, which is why you don't get your ordered car immediately.
  • Microsoft SDL: usually runs on a 6-month to 1-year project cycle.
  • Agile/Scrum: a sprint is only 1–4 weeks, and a full Agile lifecycle is often just 1–2 months — this short cycle is exactly what lets teams react quickly to new vulnerabilities or changing customer requirements that longer-cycle models can't handle well.

2. Kanban

Origin: First used by Toyota to efficiently produce car parts; adapted into software engineering around 2004; a Microsoft project applied it in 2010; built on 5 core principles.

Lecture insight — the original factory-floor Kanban ~02:31–07:19

At Toyota, large parts bins were divided into sections by part type for workers assembling cars. As a worker used up a fast-depleting part (e.g., a part with only one unit per car), a support worker would watch the worker's task load and the remaining part inventory, and proactively refill the bin so the line kept moving efficiently. That visual, "watch what's running low and reallocate help accordingly" idea is the root of Kanban.

In software, this became a visual board showing whether each task/test is in an early, nearly-done, or completed state — so anyone can see project progress at a glance. If one developer finishes their assigned tests early, a manager can look at the board and reassign them to help a teammate who's still working. Core idea: visually surface work status/progress so a team or organization can allocate effort more efficiently. (Scrum has a similar visual mechanism too — see the Burndown Chart section below.)

3. Scrum — Overview

Core idea: a product owner brings a set of requirements; the team plans how/when they'll deliver features that satisfy those requirements, then executes in short, repeated cycles with daily check-ins.

Scrum components

  • Scrum Master: removes blockers slowing the dev team down; coordinates scrum events/meetings.
  • Product Owner: defines and prioritizes items for the Product Backlog; maintains continuous communication with the dev team.
  • Development Team: the developers themselves.
  • Product Backlog: the customer's wish list — acceptance criteria, vulnerabilities to consider, desired features, etc.
  • Sprint Backlog: the specific work/plan chosen by the dev team + product owner at the start of a sprint.
  • Burndown Chart: a chart of remaining work vs. time.
Lecture insight — Scrum's rhythm, end to end ~35:41–37:22

Putting it all together: the customer (product owner) decides what needs to be done → the team forms and decides how in the Sprint Planning Meeting → that produces the Sprint Backlog → the team executes it under the Scrum Master for 1–4 weeks → the whole team holds a formal Sprint Review (and Sprint Retrospective) once per sprint → meanwhile, every single day, the team shares individual progress in a Daily Scrum Meeting → and each member's real-time progress feeds the Burndown Chart.

4. Epic / User Story / Task & the Backlogs

Epic → User Story → Task hierarchy

TermMeaningExample
EpicA large chunk of work spanning multiple sprints; has a rough description but no detailed spec — essentially the project's final goal"App users can look up and trade home prices"
User StoryA single-sticky-note-sized requirement, written in plain user language, describing one feature from the user's point of view — the smallest unit of requirement"App users should see nearby housing prices collected via GPS + internet"
TaskA very concrete unit of work needed to fulfill a story; one story can contain multiple tasks"Process GPS signal," "perform network communication," "render mobile UI"
Story PointThe relative development time/effort estimated to complete a user story—
Lecture insight — why "Epic" has no fixed platform/approach ~11:01–14:49

An Epic is basically the project's ultimate goal — e.g., "build a mobile finance app." Because that goal is achieved gradually, over many sprints, the specific "how" (which platform, which exact features) isn't decided at the Epic level. Those details only emerge once you break the Epic into User Stories (e.g., "provide transfer service," "provide balance inquiry," "provide loan service") and then into Tasks.

Product Backlog vs. Sprint Backlog

Product BacklogSprint Backlog
ScopeThe full customer wish list — acceptance criteria, vulnerabilities to consider, all desired featuresA subset of stories chosen from the Product Backlog for this sprint
Decided inOngoing / Product Owner's responsibilityThe Sprint Planning Meeting
Selection criterion—As many user stories as can realistically be completed within the sprint window, at a level that yields a workable result
Class note — format doesn't matter, content does ~18:44–19:44

There's no mandatory template for a Sprint Backlog — it doesn't have to explicitly separate Epic / User Story / Task. What actually matters is that three things are unambiguous: Who (the assignee/task), What (the user story), and How (the sub-details of the task). Any layout that makes those three clear is acceptable.

5. Scrum Meetings (Ceremonies)

5.1 Sprint Planning Meeting

  • Overall planning: focuses on understanding what the user wants, via the Product Owner (the user's representative). The Scrum Master reviews the Product Backlog to see which items were ranked highest, and discusses the background/goals with the team to understand the Product Owner's intent.
  • Detailed planning: establishes a concrete plan for how the top-priority items will be implemented; decides what will be developed from the prioritized backlog; produces the Sprint Backlog and estimates time needed for each task.
Lecture insight ~08:18–09:18

Think of the Sprint Planning Meeting as a project kickoff meeting — deciding how the work will be carried out and what the final deliverable will look like.

5.2 Daily Scrum Meeting

  • Held standing up, at a fixed time each day, short (~15 minutes)
  • Checks progress only — is the sprint backlog being developed properly?
  • All team members attend
  • Each person states what they did yesterday and will do today
  • Each person briefly mentions blockers/difficulties
  • Completed sub-tasks are moved to "done"; the Sprint board is updated; the day's remaining work is logged on the Burndown Chart
Lecture insight — informal by design ~10:13–11:01

Despite the name, a Daily Scrum isn't a formal presentation with slides — the lecturer jokingly compared it to a "smoke-break chat": roughly 10–15 minutes where people quickly say what they've built so far, flag that a teammate's function might get called by theirs, and coordinate accordingly. The point is purely to share current status, not to plan the project.

Key distinction: Planning Meeting vs. Daily Meeting ~24:15–25:19

Sprint Planning Meeting = deciding who does what, how, and by when (setting the rules — like a project kickoff). Daily Scrum Meeting = sharing whether development is going well according to those already-set rules (status-sharing only). Their purposes are distinctly different.

5.3 Sprint Review

  • Reviews the working product produced at the end of a single sprint cycle (2–4 weeks)
  • Focuses on whether sprint goals were met, checking work/output and overall business value
  • The team demonstrates the sprint's results to attendees (including the customer) and checks how well requirements were satisfied
  • The Scrum Master may run a short retrospective on what went well/could improve
  • Kept to 4 hours or less
Key concept link — Sprint Review = Validation (V-model terms) ~27:16–28:58

Class exercise: "In V-model terms, what does the Sprint Review correspond to?"

Answer: demonstrating the sprint's output to stakeholders and checking how well it satisfies requirements is exactly the definition of Validation — "are we building the right product?" (Recall Verification = checking whether design matches requirements and implementation matches design.) Since the Sprint Review is done with the customer present, it leans heavily toward Validation, even though some verification-style checking happens too.

Lecture insight — why only 4 hours? ~29:42–30:34

Since Agile's whole premise is a very short development cycle, spending too long on ceremonies and meeting write-ups would defeat the purpose — so Scrum explicitly caps the review at 4 hours. (The lecturer noted that "real" corporate/R&D meetings routinely run 5–6 hours including meals — so 4 hours is actually a deliberately tight constraint by comparison.)

Lecture insight — meeting minutes matter, but stay lean ~31:26–33:12

Producing meeting minutes is itself real work — the lecturer recalled that as a new hire, being asked to write minutes seemed trivial until getting corrected: good minutes need to clearly capture who asked for what, how the team responded, and what changes/direction that implies for the project — not a verbatim transcript. Agile's guideline is to keep this documentation as lean as possible (sometimes skipping formal minutes altogether), which is part of why Scrum relies on frequent, lightweight **Daily** meetings instead of heavy documentation.

5.4 Sprint Retrospective

  • Looks back on the sprint's activities and output; checks for improvements and whether team rules/standards were followed
  • Focuses on identifying and amplifying strengths rather than hunting for weaknesses
  • Not a "solve the problem" meeting — just identify and log issues
  • Compares estimated vs. actual velocity, and analyzes the gap if it's large (process quality itself is not measured)
Lecture insight — the point of the retrospective ~28:58–29:42

If one teammate finished faster than another, the retrospective is where the team hears how they did it, so others can adopt the same approach next time — it's about spreading lessons learned across the team, not assigning blame.

6. Burndown Chart

  • Shows how work is progressing vs. plan, as remaining work per day
  • Since it tracks remaining work, the chart trends downward over time
  • X-axis: time (days within the sprint cycle)
  • Y-axis: estimated days of completed work (expressed in story points)
  • Planned line (dotted): remaining work per day as originally planned
  • Actual line (solid): remaining work per day as work actually proceeds
Lecture insight — why leaders need this chart ~21:34–23:38

An individual developer can track their own progress just by working. But a project lead, who isn't directly coding, has a hard time knowing at a glance how far along each piece of work is. The Burndown Chart solves this: if it shows one developer (e.g., "Kim Hee-seok" in the example table) has finished their assigned sprint items early and is now idle, the Scrum Master can reassign them to help with another task (like grade registration or course setup) — reallocating effort based purely on what the chart shows.

7. Extreme Programming (XP)

Core idea: prioritizes source code over documentation, and individual responsibility/courage over organized process. Programmers write test code as they code, and the whole project runs on a test-driven basis. 12 rules help the team react even faster than usual to changing requirements.

Lecture insight — XP ≈ Build & Fix, but structured ~37:22–39:14

XP is essentially a more disciplined evolution of the Build & Fix model: write code → test it → if a bug is found, go back and fix, then retest the latest version → once no bugs are found, release with user sign-off. It's structurally very similar to Build & Fix (code → test → fix loop), just wrapped in more systematic practices (small releases, pair programming, TDD, etc.) that make the loop safer and faster.

The 12 XP Rules

  1. User Stories (Planning): like use cases — defines the customer's required feature set (functions, value, priorities); used later for cost estimation and management
  2. Small Releases: simple but frequent updates; every new requirement is integrated and the system re-released quickly
  3. (System) Metaphor: developers follow naming conventions for objects/methods, to keep everyone's mental model of the design aligned
  4. Collective Ownership: code review isn't limited to one person — the whole team reviews any given piece of code
  5. Coding Standard: the whole team follows a unified coding style/format
  6. Simple Design: design should be simple enough for newcomers to understand quickly
  7. (Code) Refactoring: remove duplicated or unnecessary code
  8. Testing (TDD): develop based on automated unit tests first; release only after tests pass
  9. Pair Programming: two people work together on a given piece of code — one writes, the other reviews and suggests improvements
  10. Continuous Integration: developers always keep the product in a fully integrated (buildable) state
  11. 40-hour Workweek: weekly hours capped (the slide says no more than 45 hrs/week) so the team stays sharp
  12. On-site Customer: the customer is fully embedded in development — answering team questions, setting priorities, resolving disputes as needed
Class discussion — why Pair Programming? ~40:13–41:27

Question: "Wouldn't adding one more coder just be faster on their own?"

Answer: pair programming exists to catch what a solo developer would miss. Just as a classmate might tell you "you also need to study this," or a reader might interpret your writing completely differently than you intended, code can also "work as expected" from the author's point of view while actually implementing the wrong logic — a second person reviewing catches this.

Worked example — Fault vs. Error vs. Failure ~42:37–46:21

Definitions:

  • Fault (결함) — an incorrect part of the code itself.
  • Error — a variable or program state that deviates from the intended one, caused by a fault.
  • Failure — an incorrect (externally observable) output result, caused by that erroneous state.

Scenario: a developer intends to implement y = x², but accidentally codes y = 2x. The developer's test criterion is: "if x = 1, y should output 4."

Test inputFault present?Error present?Failure present?Why
x = 2 (test checks y=4 when x=2)YesNoNoWith x=2, 2x = 4 — the wrong code coincidentally produces the expected output, so nothing looks wrong from the outside, even though the code itself is objectively incorrect (a fault).
x = 1 (test checks y=2 when x=1)YesYesYesThe intended y=x² should give y=1, but the coded y=2x gives y=2 — the wrong internal state (error) now surfaces as a visibly wrong result (failure).

Takeaway: a fault can exist silently in code without ever producing an observable error or failure, depending on which inputs are tested — which is exactly why relying on a single developer's own testing isn't reliable, and why Pair Programming / broader test coverage matters.
